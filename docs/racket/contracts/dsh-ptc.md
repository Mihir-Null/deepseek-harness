# Interface contract: `dsh-ptc`

This is the binding interface for `racket/dsh-ptc/`. It covers programmatic tool calling (PTC): the runtime Service Definition `ptcRuntime`, the PTC tool executor with its reserved `run_code` transport and generated SDK prompt text, three runtime providers (Node, CPython and a Racket-native extension), the workflow Service Definition `workflowEngine`, the workflow engine that runs scripts in the Node PTC process, and the model-facing `workflow` tool. Sources: [recon 09](../recon/09-ptc-workflow.md) (cited as R9 with its section), [recon 20](../recon/20-racket-mechanisms.md) (cited as R20), and `packages/ptc-runtime/*/src`, `packages/core/tool-executor-ptc/src`, `packages/workflow/*/src` and `packages/experimental/ptc-runtime-python/{src,py}` at commit `e8f7b93a3`. When this document and the TypeScript disagree about behaviour, the TypeScript is right and this document gets fixed. When they disagree about names and argument order of the Racket surface, this document is right. Read [dsh-session.md](dsh-session.md), [dsh-llm.md](dsh-llm.md), [dsh-tools.md](dsh-tools.md), [dsh-agent.md](dsh-agent.md) and [dsh-exec.md](dsh-exec.md) first; this contract uses their vocabulary without repeating it (`absent`, jobjects, `define-session-event`, cancel events of `dsh-llm/cancel`, `make-tool`, `tool-execution`, the staged pipeline, `gen:tool-approval`, `gen:agent`, `spawn-spec`, `execution-policy`, `confined-argv`).

Package: directory `racket/dsh-ptc/`, collection `dsh-ptc`, `(define deps '("base" "sandbox-lib" "cordis" "cordis-data" "cordis-schema" "dsh-util" "dsh-session" "dsh-llm" "dsh-tools" "dsh-agent" "dsh-exec"))`, `(define build-deps '("rackunit-lib" "dsh-test-support"))`. It must not require `dsh-fs`, `dsh-subagent`, `dsh-automation` or `dsh-session-store`: their services are reached by service key through generic ports (`dsh-llm/ports`, `dsh-exec/ports`, `dsh-ptc/ports`) or, for `subagents`, through one private late-binding module (Open question 3). Node and Python are never needed to build or to pass `raco test`; tests that start a sidecar skip with a visible message when the interpreter is absent (ADR 0009).

## Data

Process-local values are structs. Values that are logged, sent over a pipe or handed to listeners of other packages are jobjects with the dsh keys in the dsh order. `cancel` is a cancel event of `dsh-llm/cancel` or `#f`; `#f` stands for an omitted `signal`.

### Runtime seam (`dsh-ptc/runtime`; `ptc-runtime/src/types.ts`, `image.ts`)

```racket
(struct ptc-error-class (name member-name-property) #:transparent)          ; both string?
(struct ptc-binding-namespace (global functions error-class) #:transparent)
;; global : string?; functions : (listof (cons/c string? procedure?)), in declaration order, names unique;
;; error-class : (or/c ptc-error-class? #f)
(struct ptc-binding (proc schema) #:property prop:procedure 0)              ; schema : (or/c jobject? #f), a tool schema
(struct ptc-image (path attachment) #:transparent)                          ; path : absolute string; attachment : image ref jobject
(ptc-program-format? v)                           ; 'function-body 'repl 'script 'scoped-repl
(struct ptc-timeout (default-ms max-ms) #:transparent)

(ptc-run-request? v)
(make-ptc-run-request #:program program #:bindings namespaces
                      #:discard-completion? [discard? #f] #:state-owner [owner #f] #:cwd [cwd #f]
                      #:timeout-ms [timeout-ms absent] #:sandbox-policy [policy #f] #:cancel [cancel #f]) -> ptc-run-request?
(struct ptc-run-spec (program discard-completion? state-owner bindings cwd timeout-ms sandbox-policy cancel) #:transparent)
(ptc-run-request->spec request #:cwd cwd #:timeout-ms timeout-ms #:sandbox-policy [policy (ptc-run-request-sandbox-policy request)]) -> ptc-run-spec?

(struct ptc-output-text (text) #:transparent)
(struct ptc-output-image (attachment) #:transparent)
(ptc-output? v)                                   ; either of the two
(struct ptc-run-sandbox (mode denied? enforcement) #:transparent)           ; enforcement : (or/c #f 'full 'partial)
(struct ptc-run-failure (kind message) #:transparent)
(ptc-failure-kind? v)   ; 'exception 'timeout 'abort 'worker-exit 'invalid-output 'output-limit 'protocol 'sandbox-unavailable
(struct ptc-run-result (sandbox value output error) #:transparent)
;; sandbox : (or/c ptc-run-sandbox? #f); value : jvalue or absent; output : (listof ptc-output?); error : (or/c ptc-run-failure? #f)
(ptc-run-sandbox->jvalue s) -> jobject?           ; {mode, denied, enforcement?}
```

A binding function is `(-> jvalue? any/c)`: it takes the decoded arguments, may wait, and returns a jvalue or a `ptc-image`; a raise is a rejection of the call inside the program. A provider calls it from a task, under the parameterization captured when `ptc-runtime-run` was entered. A `ptc-binding` is such a procedure that also carries the tool schema it was made from; providers that do not use the schema apply it like any procedure. Function names are arbitrary strings (`__proto__` and `constructor` are ordinary names). `state-owner` is any value with identity (`scope-key?` of `dsh-tools/scope`) or `#f`; omission requests a fresh environment. In a request `timeout-ms` is `absent` (provider default), `#f` (no deadline, dsh `null`) or a number; in a spec it is `#f` or a positive number, and `cwd` is an absolute path string. Adjacent text entries of an output concatenate without separators. The eight failure kinds are independent outcomes.

```racket
(define-generics javascript-syntax
  (javascript-check-script javascript-syntax source filename line-offset))   ; -> (or/c #f string?); waits
```

`gen:javascript-syntax` is a Racket-only interface that the Node provider's service value also implements: it compiles `source` as a JavaScript Script without running it and returns `#f`, or the JavaScript `String(error)` text of the syntax error. The workflow engine needs it because Racket has no JavaScript parser (rule 160).

### Node control protocol records (`dsh-ptc/node`; `ptc-runtime-node/src/protocol.ts`, `rpc.ts`, `json-wire.ts`)

All are jobjects written with exactly these keys in this order.

| Record | Keys |
|---|---|
| request | `t: "q"`, `i` (id string), `m` (method), `a` (argument list) |
| notification | `t: "q"`, `m`, `a` |
| success reply | `t: "s"`, `i`, `r` |
| error reply | `t: "s"`, `i`, `e: {message}` |
| program boot data | `code`, `programFormat`, `retainsState`, `initialization?`, `maxOutputBytes`, `discardCompletion`, `namespaces: [{global, names, errorClass?: {name, memberNameProperty}}]` |
| program result | `value?` (a wire token list), `error?: {kind, message}` with `kind` one of `exception`, `invalid-output`, `output-limit` |
| image token | `kind: "image"`, `id`, `attachmentId`, `path`, `width`, `height` |
| array token | `kind: "array"`, `length` |
| object token | `kind: "object"`, `keys` |

Methods and their direction are in rule 110. A *wire token list* (dsh `PtcJsonWire`) is a non-empty flat list holding one JSON value in pre-order (rule 113).

### Python protocol frames (`dsh-ptc/python`; `experimental/ptc-runtime-python/src/protocol.ts`, `py/protocol.py`)

One jobject per line. Host to child: `{type: "boot", cpuSeconds, addressSpaceBytes, maxLogBytes, maxValueBytes, namespaces: [{global, names, errorClass?: {name, memberNameProperty}}]}`, `{type: "run", program}`, `{type: "reply", id, ok: true, value}`, `{type: "reply", id, ok: false, message}`. Child to host: `{type: "boot-ack"}`, `{type: "call", id, global, name, args}`, `{type: "log", text, truncated?, open?}`, `{type: "done", value?, error?: {kind, message}}` with `kind` one of `exception`, `invalid-output`, `output-limit`, `timeout`.

### Executor data (`dsh-ptc/events`, `dsh-ptc/executor`; `tool-executor-ptc/src/types.ts`, `runtime-types.ts`)

```racket
(define-session-event tool/ptc-dispatch-start #:type "tool/ptc-dispatch-start"
  #:fields ([root-call-id "rootCallId" string?] [parent-call-id "parentCallId" string?]
            [sub-call-id "subCallId" string?] [name string?] [arguments jvalue?]))
(define-session-event tool/ptc-dispatch #:type "tool/ptc-dispatch"
  #:fields ([root-call-id "rootCallId" string?] [parent-call-id "parentCallId" string?]
            [sub-call-id "subCallId" string?] [name string?] [arguments jvalue?]
            [error? "isError" boolean?] [error jobject? #:optional]
            [content (listof jobject?)] [meta jvalue? #:optional]))
ptc-mode-source                                   ; the jobject {kind: "ptc-mode"}
(ptc-mode-source? v) -> boolean?
(ptc-dispatch-log? v) -> boolean?                 ; immutable hasheq with the keys below
```

Data keys in write order: `rootCallId`, `parentCallId`, `subCallId`, `name`, `arguments` for the start; the same five, then `isError`, `error?` (`{name, code, reason?}`), `content`, `meta?` for the settle (`ptc.ts:611-624`). Both are log-only: not surface events, not ignorable, never part of derived messages. The golden lines are in R9 "Session events". A *dispatch log* (dsh `PtcDispatchLog`) is the payload of `tools/ptc-dispatch-log`: an immutable `hasheq` with `'exec` (the outer `tool-execution`), `'agent`, `'subCallId` (string), `'name` (string), `'isError` (boolean) and `'content` (list of content blocks). It is a hash, not a struct, so that a listener of another package (`dsh-fs` spill policy) reads it with `hash-ref` or `jref` without requiring this package.

The canonical value of `run_code` (dsh `RunCodeOutput`) is the jobject `{logs: [string…], sandbox?: {mode, denied, enforcement?}, result?}` in that key order. A sub-call id is `<outer call id>:ptc:<n>`.

### Workflow data (`dsh-ptc/workflow`; `workflow/src/types.ts`, `runtime-types.ts`)

Jobjects, keys in this order: workflow meta `{name, description, whenToUse?, phases?: [{title, detail?, provider?, model?}]}`; run info `{id, meta}`; agent info `{seq, label, childId, phase?}`; agent end info `{seq, label, childId, phase?, outcome}` with `outcome` one of `completed`, `failed`, `cancelled`; result info `{stopReason, error?, agentsStarted}`.

```racket
(workflow-start-request? v)
(make-workflow-start-request #:script script #:meta meta #:parent agent #:args [args absent]
                             #:subagent-provider [provider #f] #:max-total-agents [n #f] #:cancel [cancel #f])
(struct workflow-result (value stop-reason error agents-started) #:transparent)
;; value : jvalue ('null when the script returned nothing); stop-reason : "completed" "cancelled" "error"; error : (or/c string? #f)
(workflow-run? v)                                 ; opaque
(make-workflow-run #:id id #:meta meta #:result task #:cancel cancel #:dispose dispose) -> workflow-run?
(workflow-run-id r) -> string?                    ; a lowercase version 4 UUID
(workflow-run-meta r) -> jobject?                 ; the validated, normalised meta
(workflow-run-result-evt r) -> evt?               ; ready when settled; its value is the workflow-result
```

Guest protocol records (`workflow-ptc/src/guest-types.ts`, `types.ts`), jobjects: worker init `{meta, body, args?, limits: {maxConcurrentAgents, maxTotalAgents, maxItemsPerCall, syncTimeoutMs}}`; child start request `{prompt, schema?, provider?, model?}`; started child `{callId, childId}`; child result `{output, stopReason, structured?}`; progress events `{type: "phase", title}`, `{type: "log", message}`, `{type: "agent-start", info}`, `{type: "agent-end", info}`.

### Ports (`dsh-ptc/ports`)

```racket
(define-generics workflow-job-port
  (workflow-job-start! workflow-job-port spec))                  ; -> string? (the job id); may raise (admission, or the starter's own raise)
(struct workflow-job-spec (label owner call-id root-call-id run))
(struct workflow-job-handle (update-progress! append-log!))      ; (-> string? void?) each; append-log! writes on channel "log"
(struct workflow-job-hooks (done cancel))                        ; done : evt whose value is a workflow-job-outcome?; cancel : (-> (or/c string? #f) void?)
(struct workflow-job-outcome (status detail result) #:transparent)   ; status : "completed" "killed" "failed"; detail, result : (or/c string? #f)
```

`run` of a spec is `(-> workflow-job-handle? workflow-job-hooks?)`, called by the registry after admission; a raise from it propagates out of `workflow-job-start!` and registers no job. `owner` is an agent id. The job kind is always `workflow`. The service key is `jobs` (provider: `dsh-automation`), read with `port-get` of `dsh-llm/ports`. This port exists beside `gen:job-registry-port` of `dsh-exec/ports` because a workflow job needs a progress line, a `log` channel and a result text, which that port does not carry.

### Errors (`dsh-ptc/errors`)

Substructs of `exn:fail:harness` made only by these constructors; the dsh error name and code are the persisted identity.

| Constructor | dsh name | Code | Message |
|---|---|---|---|
| `(make-code-run-failed-error message)` | `CodeRunFailedError` | `CODE_RUN_FAILED` | as given |
| `(make-code-reset-failed-error message)` | `CodeResetFailedError` | `CODE_RESET_FAILED` | as given |
| `(make-ptc-aborted-error message)` | `AbortError` | `ABORTED` | as given (`tool call aborted` or `tool call aborted: <detail>`) |
| `(make-workflow-error code message #:fatal? [fatal? #t] #:cause [cause #f])` | `WorkflowError` | one of `workflow-error-codes` | as given |

`workflow-error-codes` is `SCRIPT_PARSE`, `META_INVALID`, `INVALID_ARGUMENT`, `UNSUPPORTED_OPTION`, `UNSUPPORTED_SCHEMA`, `AGENT_CAP`, `ITEM_CAP`, `AGENT_START`, `AGENT_RESULT`, `RESULT_UNSERIALIZABLE`, `CANCELLED`. `(workflow-error-fatal? e)` reads the flag; `(fatal-workflow-error? v)` is true for a workflow error whose flag is set. `(struct exn:fail:tool-call-limit exn:fail (limit call-number))` is dsh `ToolCallLimitExceededError`, a plain exception used as a cancel reason; `(make-tool-call-limit-error limit call-number calls-per-minute tool-name)` builds it with the message of rule 54.

## Services

`x` is a context or a handle for the service; "the caller's context" is `(use-context x)`. A seam with interchangeable providers is a generic interface whose methods take the provider's value first; the context-first procedures read the service value and call it.

### `ptcRuntime`

`(define-service ptc-runtime-service 'ptcRuntime #:contract ptc-runtime?)` in `dsh-ptc/runtime` defines `ptc-runtime-service-key`, `ptc-runtime-service-ref`, `ptc-runtime-service-get` and `provide-ptc-runtime-service`. One provider per context. It knows nothing about tools or sessions.

```racket
(define-generics ptc-runtime
  (ptc-runtime-language ptc-runtime)                       ; -> string?, lowercase: "typescript", "python"; extension: "racket"
  (ptc-runtime-isolation ptc-runtime)                      ; -> string?, a substrate descriptor: "process", "sandbox-evaluator"
  (ptc-runtime-program-format ptc-runtime)                 ; -> ptc-program-format?; fallback 'function-body
  (ptc-runtime-retains-state? ptc-runtime)                 ; -> boolean?; fallback #f
  (ptc-runtime-execution-instructions ptc-runtime)         ; -> string?; fallback ""
  (ptc-runtime-sandbox-mode ptc-runtime)                   ; -> (or/c sandbox-mode? #f); fallback #f (the provider cannot confine)
  (ptc-runtime-timeout ptc-runtime)                        ; -> (or/c ptc-timeout? #f); fallback #f (no per-call timeout)
  (ptc-runtime-resolve ptc-runtime request)                ; -> ptc-run-spec?; does not wait
  (ptc-runtime-run ptc-runtime spec)                       ; -> ptc-run-result?; waits
  (ptc-runtime-release! ptc-runtime owner)                 ; -> void?; waits; fallback does nothing
  (ptc-runtime-register-initializer! ptc-runtime program)) ; -> (-> void?); fallback raises
(ptc-resolve x request) -> ptc-run-spec?                   ; (ptc-runtime-resolve (ptc-runtime-service-ref x) request)
(ptc-run x spec) -> ptc-run-result?
(validate-ptc-bindings namespaces who) -> (listof ptc-binding-namespace?)   ; rule 2; who : string?, the message prefix
```

| Operation | Semantics and errors | Effects |
|---|---|---|
| `ptc-runtime-resolve` | Validates explicit choices and fills provider defaults: an absolute `cwd`, a numeric deadline or `#f`, the policy when the provider confines. Raises `exn:fail` for an unsupported or invalid choice. `ptc-runtime-run` never fills a default. | none |
| `ptc-runtime-run` | Program, budget, cancellation and substrate failures return a result whose `error` is set; only caller misuse raises (invalid bindings, a spec this provider did not resolve, a call after disposal). The output is in emission order. Cancellation is the spec's `cancel`. | none on any context; the provider tracks the run and ends it when the provider unloads |
| `ptc-runtime-release!` | Releases the owner's retained environment and waits for its resources. Raises when cleanup fails; the failure stays retryable. | none |
| `ptc-runtime-register-initializer!` | Registers source evaluated once per new environment. At most one; before the first run admission. The fallback raises `PTC runtime: environment initialization is unsupported`. The result is an idempotent procedure that stops admission, cancels and drains admitted runs, releases environments and waits; the caller owns it. | none |

### Waiting and cancellation

- `ptc-runtime-run`: the spec's `cancel`. A cancelled run returns a result with failure kind `abort`. The provider never abandons the process or evaluator it started: it returns after cleanup.
- `ptc-runtime-release!` and the disposer of `ptc-runtime-register-initializer!` take no cancel event: cleanup must complete.
- `tool-executor-execute`: the batch input's cancel event, as in `dsh-tools`. A `run_code` body observes `(tool-execution-cancel exec)`; it returns only after every started sub-call has settled and been logged (rule 52).
- A binding call made by a program is cancelled by the run-scoped cancel source of rule 43, never by a break.
- `ptc-executor-reset!` takes no cancel event.
- `workflow-start`: the request's `cancel` governs the run after publication; before publication the call is cancelled only by a break of the calling task. `workflow-run-result` and `workflow-run-dispose!` take no cancel event; a break of the waiting task ends that wait only.
- `javascript-check-script` and the private strip operation take no cancel event; a caller that must stop waiting wraps the call in a `choice-evt` with its own cancel event (the Node worker does, rule 95).
- No procedure of this package catches a break. A break of a task that waits inside one of them propagates; processes, evaluators and child agents keep running until their cancel event, their owner's disposal or their custodian stops them.

### `run_code` (reserved transport; `tool-executor-ptc/src/ptc.ts:311-865`)

## Behaviour

Numbering is for tests. "Raise" without a type means `exn:fail` with the exact message. Handlers that turn a raised value into a result never catch `exn:break`. `<JSON x>` means the JSON text of the string `x`. Lengths are UTF-8 bytes unless a rule says UTF-16 units.

**Seam and data plane** (R9 "Services", "G. Output accounting"; `ptc-runtime/src/index.ts:47-93`, `ptc-runtime-node/src/bindings.ts`, `output-json.ts`, `output-ledger.ts`)

1. Portable names. A binding global and an error-class name must match `^[A-Za-z_][A-Za-z0-9_]*$` and not be in `portable-reserved-words`, the 71 words of `PORTABLE_RESERVED_WORDS` (`index.ts:82-93`), copied in source order. `reserved-binding-globals` is `console`, `inspect`, `Image`, `__dsh_main__`, `__builtins__`, `__name__`, `__debug__`. `reserved-error-members` is `name`, `message`, `stack`, `args`, `with_traceback`, `add_note`; a member name is also refused when it is empty or matches `^__.+__$`. Every provider enforces all of them, so a namespace list valid on one is valid on all.
2. `(validate-ptc-bindings namespaces who)` raises before any process or evaluator starts. First pass, per namespace in order: `<who>: binding global <JSON g> is not a usable identifier` (pattern or reserved word); `<who>: reserved binding global <JSON g>`; `<who>: duplicate binding global <JSON g>`. Second pass, per namespace with an error class in order: `<who>: binding error class <JSON n> is not a usable identifier`; `<who>: reserved binding global <JSON n>`; `<who>: duplicate injected global <JSON n>` (the name is a binding global or an earlier error-class name); `<who>: binding error member property <JSON m> is not usable`. The Node provider passes `dsh-ptc-runtime-node` and the Racket-native provider `racket:ptc-runtime-racket`; the Python provider has its own texts (rule 150).
3. `(ptc-json-snapshot v)` returns `v` as an immutable jvalue when `(lossless-json? v)` of `dsh-session/lossless` holds, and `#f` otherwise. A hash becomes a jobject in the key order `cordis-data` gives it. Because jvalues are immutable, the two detached copies dsh makes of binding arguments (one dispatched, one logged) are one value here.
4. `(json-string-bytes-up-to text max)` is the byte length of the JSON string literal for `text`, or `#f` when it exceeds `max` or `max` is below 2: 2 for the quotes; `"` and `\` cost 2; a character below U+0020 costs 2 when it is U+0008, U+0009, U+000A, U+000C or U+000D and 6 otherwise; a character above U+FFFF costs 4; any other its UTF-8 length. `(json-value-bytes-up-to v max)`: `'null` 4, `#t` 4, `#f` 5, a number the UTF-8 length of `(js-number->string n)`, a string its string cost, a container 2 plus 1 per separator, an object key its string cost plus 1.
5. `(truncate-json-string-bytes text max)` is the longest prefix of whole characters whose string cost is at most `max`; `""` when `max` is below 2; `text` itself when all of it fits.
6. `(make-output-ledger max-bytes [overflow-message #f])` starts at 2 bytes (the text `[]`). `(ledger-admit! l entry)` charges the entry plus 1 separator after the first and returns `#f`, charging nothing, when it does not fit; a text entry costs its string cost and an image entry the value cost of `{type: "image", attachment}`. `(ledger-success l output value)` returns the result, or the limit result when a present `value` does not fit the remaining bytes. `(ledger-failure l output failure)` does the same for the failure message's string cost.
7. `(ledger-limit l output)` (`output-ledger.ts:44-73`): the diagnostic is the overflow message, else `outer output exceeded <max> bytes`; reserve its length plus 2; keep entries in order while they fit, counted from 2 bytes; cut the first text entry that does not fit to its rule 5 prefix (dropped when empty) and stop; stop at the first image that does not fit; the message is the diagnostic truncated by rule 5 to the bytes left. The result has kind `output-limit`. Binding arguments and results never enter a ledger.
8. Every provider captures `(current-parameterization)` when `ptc-runtime-run` is entered and calls binding functions with `call-with-parameterization` from a task of the caller's scheduler, so a binding sees the caller's parameters (the initiator of `dsh-agent` among them) whatever thread received the request.

**Executor: one `run_code` execution** (R9 "A. `run_code` execution"; `ptc.ts:392-814`, `index.ts:39-45`)

38. The executor's pipeline is `(make-tool-execution-pipeline ctx #:get get #:reject reject)`. `get` returns the reserved transport for the name `run_code` (created on first use and kept) and `(tools-executable tools name scope tool-set)` for any other name. `(reject name nested?)` returns `(make-tool-not-found-error name <hint>)` when `nested?` is false and the name is not `run_code`, with the hint ``only `run_code` is callable directly — call `<name>` from inside a `run_code` program instead``, and `#f` otherwise. A sub-call carries the outer execution's token as its parent, so it is nested and is not rejected. The executor keeps the `tools` service value and the logger it read at construction, so that settle logging works after its context became inactive.

40. 41. In the rules below *call cancel* is the event the run procedure was given: the outer cancel event, or under admission the fusion of it with that call's own cancel source.
42. Authority. When the runtime confines, the standing policy is `(sandbox-policy-resolve sandboxPolicy #:session (agent-session agent))`, or without an agent `(sandbox-policy-resolve sandboxPolicy)`; a missing `sandboxPolicy` service raises `dsh-tools: confined PTC runtime requires sandboxPolicy`. Then the working directory: `#f` without an agent; with one, `(working-directory-ensure workingDirectory agent <call cancel>)`, or `dsh-tools: run_code with an Agent requires workingDirectory` when the service is absent. Then `(check-cancelled! <call cancel>)`.

Sub-calls and the runtime observe its event. "The run is over" means it is cancelled; `<reason text>` below is the JavaScript `String` of its reason (`error->js-string` of `dsh-exec/errors`).

45. For an agent-owned call, once per pair of agent and runtime value (a weak table keyed by the agent), register on `(agent-ctx agent)` an effect labelled `PTC retained environment` whose inverse is `(ptc-runtime-release! runtime agent)`.
46. The request: `program` is `code`; `discard-completion?` is true for the languages `typescript` and `racket`; `state-owner` is the agent only when there is one and the execution's policy mode equals the standing mode (both may be absent), else `#f`; `bindings` is one namespace with global `tools`, the functions of rule 44 and the error class `(ptc-error-class "ToolCallError" "toolName")`; `cancel` is the run source's event; `cwd` and `sandbox-policy` when present; `timeout-ms` is the argument when given, else `absent`. `(ptc-runtime-resolve runtime request)` gives the spec.
47. The allowance is unlimited when the spec's deadline is `#f` and otherwise `(floor (* (/ timeout-ms 60000) maxSubCallsPerMinute))`: 2048 for the defaults. It counts attempts of one program.
48. `(ptc-runtime-run runtime spec)`. Whether it returns or raises: cancel the run source with `<tool name> settled`, then drain (rule 65 to quiescence, then wait until no settle log task remains). Queued sub-calls that never started are abandoned without events; started ones settle and are logged before the body continues. A raise of the runtime propagates after the drain.
49. Success. `logs` is the texts of the text entries in order. The value is `{logs}`, plus `sandbox` when the result has one, plus `result` when the language does not discard completions (rule 46) and the result has a value. When the output holds an image, remember `{value, output}` for this execution (rule 73).
50. A result with an error is mapped by rules 71 and 72; the raised error becomes the tool result through the pipeline.
51. When a failed run produced an image, remember `{failure, output}` for this execution, where `failure` is the error message with info `{name, code}` and the content `Error: <message>` (rule 73).
52. At return: every started sub-call has exactly one `tool/ptc-dispatch` event in the log, appended between the outer `tool/call` and `tool/result`; nothing is appended for this run afterwards; no sub-call body is still running.

**Executor: one binding call** (R9 "B. One binding call"; `ptc.ts:554-712`)

53. Called by the runtime with the decoded arguments. If the run is over, raise `<tool name> run is over (<reason text>); <name> not dispatched`.
54. Count the attempt first, so failed attempts also consume the allowance: `n` is the incremented counter. If `n` exceeds the allowance, cancel the run source with `(make-tool-call-limit-error limit n maxSubCallsPerMinute tool-name)` and raise that error. Its message is `<tool name> exceeded its limit of <limit> tool calls (<maxSubCallsPerMinute> per minute of its timeout); call <n> was not dispatched. The <tool name> program may contain an infinite loop. Check loop termination or split the work into smaller <tool name> calls.` The runtime then stops the program through its cancel path; catching the error inside the program cannot keep it alive.
55. Arguments. `(ptc-json-snapshot raw)`; `#f` raises ``tool arguments must be lossless JSON (call the tool with an arguments object, e.g. `{}`)`` and nothing is dispatched. (dsh's variant with a detail, `tool arguments must be lossless JSON: <detail>`, arises only from a throwing getter and has no counterpart.)
56. The pipeline input is `(make-tool-execution-input #:call-id "<outer call id>:ptc:<n>" #:root-call-id (tool-execution-root-call-id exec) #:name name #:schema schema #:arguments arguments #:agent agent #:tool-set tool-set #:parent (tool-execution-token exec) #:cancel <run source event>)`, with `agent` and `tool-set` only when the outer execution has them. The parent token marks the call as nested and lets result observers correlate it with the outer call.
57. Append a pending entry to the scheduler's queue, wake the driver and wait for the entry's outcome (rule 66) or for abandonment, which raises `<tool name> run is over (<reason text>); <name> tool call abandoned`.
58. With the outcome: if the run is over, raise `<tool name> run is over (<reason text>); <name> result discarded`. If the sub-call failed, raise an `exn:fail` with the failure's message only; the provider turns it into the program's `ToolCallError`, so native content and error identity do not reach the program. Otherwise return the canonical value (`tool-success-value`), not the rendered content, except by rule 59.
59. Program images apply only when the language is `typescript` and the tool is named `read_image` or `cua`. With exactly one image block in the committed content, return `(ptc-image path attachment)` where `path` is `(process-path-from-host-path fs (attachment-image-host-path attachments attachment))`; when `attachments` or `fs` is absent or either step gives `#f`, raise `Image storage must expose a readable path in the program filesystem`. With no image now but one before post-execute, raise `Image output was removed by a tool output policy.`, a line break, and the remaining text blocks joined by line breaks. For `read_image` without exactly one image, and for any tool with more than one, raise `Image-producing tools must return exactly one image`. Otherwise return the value.
60. Denials. A `tools/pre-execute` denial, a guard denial, an approval rejection or a cancelled approval is an error result of `pipeline-prepare`; the program sees a `ToolCallError` whose message is the denial reason, and the `tool/ptc-dispatch` event keeps the identity in `error`. A tool that was unregistered between enumeration and dispatch fails as an unknown tool. A sub-call cancelled by the run source settles as the pipeline's aborted result, which is an error outcome.

**Executor: the sub-dispatch scheduler** (R9 "C. The sub-dispatch scheduler"; `ptc.ts:448-547`, `:583-690`)

61. State per run, owned by one driver task: the pending queue (submission order), the commit queue (start order), the set of bodies in flight, the set of settle log tasks, and the flag `exclusive-active?`. Submissions and body completions wake the driver through a mailbox, so a wake cannot be lost. The driver runs every ordered stage; only tool bodies and settle log tasks overlap it.
62. Each driver pass, first case: the head of the commit queue has settled. Remove it and run its commit stage (rule 66); afterwards clear `exclusive-active?` when the entry started as exclusive, so the barrier covers post-execute. Next pass.
63. Second case: the pending queue has a head. If the run is over, remove it and abandon it (rule 57). Otherwise classify it now with `(pipeline-execution-mode pipeline input)`; there is capacity when `exclusive-active?` is false and, for `'exclusive`, nothing is in flight, or for `'parallel`, fewer than `maxParallelSubCalls` bodies are. With capacity: set `exclusive-active?` for an exclusive entry, record the mode, move the entry to the commit queue and run its start stage (rule 64); track the body until it finishes. Next pass.
64. Start stage, in the driver: when the outer execution has an agent, append `tool/ptc-dispatch-start` (`rootCallId` the outer root call id, `parentCallId` the outer call id, `subCallId`, `name`, `arguments`) to the agent's session; then `(pipeline-prepare pipeline input)`. A `'dispatch` outcome starts `(pipeline-dispatch pipeline exec)` in a new task whose result parks in the entry and marks it settled; any other outcome parks at once and marks it settled. A call abandoned in the queue therefore logs nothing.
65. Third case: when the three collections are empty the driver returns (quiescence); otherwise it waits for a body to finish or a submission. A driver that returned is started again by the next submission or by the drain of rule 48.
66. Commit stage, in the driver: `(pipeline-complete pipeline exec parked)` gives the result. When the call is not a program-image call (rule 59) and the result is a success whose content holds an image, defer `(make-user-message #:content content #:source ptc-mode-source)` on the outer execution with `tool-defer-context!`. Defer each of the result's additional contexts on the outer execution, in order. Call `tool-conclude-turn!` on the outer execution when the result concludes the turn. Then settle: hand the program its outcome at once (failure message, or value, content and whether an image was removed, which is true when the parked content held an image and the committed content does not), and, when there is an agent, start the settle log task of rule 67. Then, while more than `maxParallelSubCalls` settle log tasks are pending, wait for one to finish.
67. Settle log task: the logged content is `(scoped-dispatch ctx 'waterfall 'tools/ptc-dispatch-log agent (list log) #:base (service-realm-filter ctx 'tools) #:inner (lambda () content))`; if that raises, log at `warning` `tools: ptc-dispatch-log listener failed for <name>: <message>; logging the original settled content` (message by `tool-error-message`) and use the original content. Then append `tool/ptc-dispatch` with the five start fields, `isError`, `error` (the result's info as `tool-error-info->jvalue`) when it has one, `content` the logged content, and `meta` when the result has one.
68. Guarantees to test: starts are strictly in submission order; results commit in submission order even when bodies finish out of order; consecutive parallel-safe calls overlap up to `maxParallelSubCalls`, and 1 makes them serial; an exclusive call waits for the pool to drain, runs alone and blocks later starts until its commit completes; classification is read again immediately before each start; the program has its value before the log listener and the append run; ordered stages (`tool/ptc-dispatch-start`, pre-execute, guards, post-execute, context deferral) never overlap each other; an agentless run writes no events.

**Executor: results** (R9 "Tools, `run_code`"; `ptc.ts:167-285`, `:772-826`)

69. `(render-run-output value guidance output tool-name)`: walk `output` (by default one text entry per element of `logs`); consecutive text entries concatenate into one text block, skipped when empty; each image entry flushes the pending text and adds `{type: "image", attachment}`. Then the detail lines, joined by a line break into one more text block when not empty: the rendered `result` when present (rule 70); `File sandbox enforcement is partial on this host.` when `sandbox.enforcement` is `partial`; `The <mode> file sandbox denied an operation.<guidance>` when `sandbox.denied`. With no block at all the content is one text block `(<tool name> completed with no output)`. The tool's `render` calls it with the escalation guidance for the runtime mounted now (for a registered program tool, its own runtime). Golden: the `tool/result` of `ptc-turn` has the single block `captured output\nCODE_ONE+CODE_TWO\n`.
70. `(render-json-value v)`: a string is emitted as it is. Any other value is JSON with two-space indentation in the layout of `JSON.stringify(v, null, 2)`, except that a container whose members would be indented by more than 10 spaces is emitted compact, with no whitespace, together with everything inside it (`ptc.ts:183-250`); empty containers are `[]` and `{}`; numbers are `js-number->string`.
71. A failed run that is not rule 72 raises the code run failed error with the message `code run failed (<kind>): <failure text><logs text><sandbox text><guidance>`. `<failure text>` is the failure message, except that when the run source's reason is a tool-call-limit error whose message differs from it, it is the limit message, a line break and the failure message. `<logs text>` is a line break, `Captured output:`, a line break and all text output concatenated, only when there is text and no image. `<sandbox text>`, only when the result has sandbox facts, is a line break (omitted when `<logs text>` ends with one) and `File sandbox: <mode>`, then `; enforcement: <e>` when present, then `; operation denied` when denied, then `.`. `<guidance>` is the escalation guidance of the runtime when denied. For the allowance of rule 54 under the Node provider the text is therefore `code run failed (abort): run_code exceeded its limit of 2048 tool calls (1024 per minute of its timeout); call 2049 was not dispatched. …`.
72. Caller cancellation: when the failure kind is `abort`, the outer cancel event is ready and the run source's reason is not a tool-call-limit error, raise `(make-ptc-aborted-error "tool call aborted")`, or with the message `tool call aborted: <failure message>` when the runtime retains state.
73. `project-content` (called once by the pipeline before post-execute): take and forget what rules 49 and 51 remembered for this execution; nothing gives `#f`. For an error result: `#f` unless its error and content equal the remembered failure; otherwise the result's content followed by `(render-run-output {logs: []} "" output tool-name)`. For a success: `#f` unless the result's value equals the remembered value; otherwise `(render-run-output value guidance output tool-name)`. So ordered images appear only when the result is still the one the tool produced; a policy replacement stays authoritative.
74. Presentation: `present-call` gives `{card: "generic", title: <description>, kind: "execute", rawInput: <code>}`. There is no result view; the generic card reads the durable content.
75. Root `run_code` calls declare no concurrency classifier, so `execute-tool-batch` runs them one at a time in model order.

**Executor: admission, policy changes and reset** (R9 "A" step 2, "D. Host reset"; `ptc-calls.ts`, `index.ts:73-86`)

76. Calls bookkeeping, one per executor and per registered program tool: a table from session id to the set of admitted calls, each `{mode, source, cancel, done}` (`cancel` fuses the caller's event with `source`), a table from session id to a reset record, and a disposed flag.
77. Admission `(calls-run session-id cancel mode-thunk run)`: loop: while the session has a reset record, wait for it; a failed reset raises the code run failed error `Program environment unavailable: <message>. Ask the host to reset it before running more code.`; then wait for every admitted call of the session whose `cancel` is already ready; repeat until neither applies. Then `(check-cancelled! cancel)`; a disposed bookkeeping raises `PTC tool executor disposed`. Record the call with `(mode-thunk)` read now, run `(run cancel*)`, and in every case remove the record and make `done` ready.
78. The `session/event` listener: for an event whose type is `sandbox/mode`, every admitted call of that session whose recorded mode is not `#f` and differs from the event's `mode` has its source cancelled with an `exn:fail` whose message is `sandbox mode changed`.
79. Disposal (the inverse of the `PTC calls` effect): set the disposed flag, cancel every admitted call with an `exn:fail` `PTC tool executor disposed`, and wait for every call's `done` and every reset record, ignoring failures.
80. `(ptc-executor-reset! executor agent)`: read the runtime (rule 12); a runtime that does not retain state raises the code reset failed error `The PTC runtime does not retain an environment`. Otherwise reset the session: a disposed bookkeeping fails with `PTC tool executor disposed`; an unsettled reset record is shared by concurrent callers; else create the record, cancel every admitted call of the session with `PTC environment reset`, and in parallel run `(ptc-runtime-release! runtime agent)` and wait for every such call's `done`. On any failure the record stays, failed, and blocks new programs until a later reset succeeds. On success call `(agent-inject! agent (make-user-message #:content (list (text-block "Program environment reset; retained variables cleared. Completed tool effects remain.")) #:source ptc-mode-source))`, then remove the record. Any failure is raised as the code reset failed error `Program environment reset failed: <message>. State may not be cleared; retry the host reset before running more code.`

**Registered program tools** (R9 "Registered program tools"; `run-code.ts`)

81. `(make-run-code-tool ctx #:name … #:description … #:runtime … #:tools … #:limits …)` builds the transport of rules 39 to 75 under the given name with: the caller's description in place of the flavor description (rule 9); the given runtime in place of the mounted one; `limits` validated by the executor's config schema; a table of the private definitions in list order, where a repeated name raises `Program tool <name> has duplicate binding <binding>`.
82. It has its own pipeline, `(make-tool-execution-pipeline ctx #:get (lambda (name scope tool-set) <the private definition or #f>))` with no `reject`, and its own calls bookkeeping. The private definitions need not be registered. Nested calls keep approvals, guards, result policy, dispatch events and deferred contexts. It contributes no prompt section.
83. Its messages use its own name wherever rules 43 to 71 write `<tool name>` (run-over texts, the allowance, the empty-output placeholder).

**Node provider: one evaluation** (R9 "F. Node provider: one evaluation"; `ptc-runtime-node/src/worker.ts`)

One worker owns one custodian that holds the subprocess handle, its ports and its reader threads. Its state machine runs in one owner task fed by a mailbox (reader threads, the timer and the cancel event only post messages), which is the Racket form of the single JavaScript event loop the TypeScript relies on. `<retained suffix>` is `; retained variables were cleared` for a retained worker and empty otherwise.

91. If the worker's process already exited: terminate (rule 105); the result is failure `abort` `execution canceled<retained suffix>` when the cancel event is ready, else `worker-exit` with the exit message of rule 103 and the suffix; a raise from termination gives `worker-exit` `managed process cleanup failed: <message>`.
92. Otherwise create the ledger with `maxOutputBytes` and, for a retained worker, the overflow message `retained variables were cleared; outer output exceeded <max> bytes`. With a deadline, arm a timer; on expiry finish with `timeout` `execution timed out <phase> (<timeoutMs>ms)`, where `<phase>` is `during execution` once `run` was sent to the process and `before code started` before that, discarding the environment in the second case.
93. When the cancel event fires, finish with `abort`: message `execution canceled` for a retained worker, otherwise the text of the reason (the message of an exception, else `error->js-string`); the environment is discarded when `run` was not yet sent. A cancel event that is ready at entry finishes this way at once.
94. Text from the process is decoded as UTF-8 incrementally: an invalid sequence becomes U+FFFD and an incomplete sequence at the end of a read is held for the next one.
95. Erase types: `(strip format program)` through the syntax service (rule 116), waited for together with the cancel event and the deadline. A syntax error finishes the evaluation with `exception` and the parser's message, discarding the environment only when the worker has no ready process; no process is started for it. A failure of the service itself finishes with `worker-exit` `TypeScript syntax service failed: <detail>` under the same discard rule.
96. If the worker's process is ready, send `run` (rule 101). Otherwise start it (rule 97); its `ready` notification sends `run`. A failed start finishes with `sandbox-unavailable` when the failure is the sandbox unavailable error, or the process was confined and `(runner-spawn-failure? failure (car confined-argv) cwd)` holds, and with `worker-exit` otherwise; the message is the failure's with the retained suffix.
97. Launch (`worker.ts:311-329`, `launch.ts`). The executable is `(subprocess-resolve-executable subprocess launch.executable #:cancel <worker cancel>)`. The argv is the executable, `--max-old-space-size=<maxOldGenerationSizeMb>`, `--experimental-vm-modules`, the runner path and `<maxMessageBytes>`, numbers written with `js-number->string`. The runner path is `launch.bootstrapPath` when given, else `(process-path-from-host-path fs <host path of sidecar/ptc-runner.mjs>)`; `#f` raises `PTC runtime bootstrap is unavailable in the subprocess execution world: <host path>`. Unless the policy mode is `danger-full-access`, the argv becomes `(confined-argv-argv (sandbox-confine sandbox argv policy #:cancel …))`. The spawn spec has that argv, the cwd, stdin `'ignore`, stdout and stderr `'pipe`, `control?` true, `grace-ms` `graceMs`, and an `env` that maps to `#f` every name of `(scrubbed-parent-env)` whose upper-case form is not `PATH`, `PATHEXT`, `SYSTEMROOT`, `WINDIR`, `TEMP`, `TMP` or `ELECTRON_RUN_AS_NODE`. A handle without a control channel or without both output ports raises `subprocess provider did not supply the requested control and output pipes`. The control channel is the pair of `subprocess-handle-control`; the child finds it on descriptor 7 with `DSH_SUBPROCESS_CONTROL=pipe`, exactly as under dsh (Racket design notes, "Descriptor 7").
98. Output. Every decoded chunk of stdout and stderr is admitted to the ledger as a text entry for as long as the evaluation is the worker's active one, cleanup included; stderr is also kept as a tail of at most `maxOutputBytes` UTF-16 units for exit diagnostics. A `log` notification is admitted unless the evaluation has settled. An `image` notification appends the registered image at the current position unless the evaluation settled or overflowed. The first entry that does not fit marks the evaluation as overflowed, keeps an overflowing text entry in the output (rule 7 cuts it), and finishes with `output-limit` `output limit exceeded`, discarding the environment; later text is dropped.
99. `invoke(global, name, wire)` (`worker.ts:376-406`). Without a ready process and an active evaluation: protocol failure `binding call arrived without an active PTC evaluation`. For a settled evaluation: error reply `PTC evaluation ended before the binding completed`. Look the function up by exact name in the namespace of that global. A non-retained worker and no such function: protocol failure `program requested an undeclared binding`. Decode the arguments (rule 114); failure: protocol failure `binding arguments must be lossless JSON`. `bytes` is the UTF-8 length of the JSON text of the wire list; when `maxPendingCalls` calls are pending, or the pending bytes plus `bytes` exceed `maxMessageBytes`: protocol failure `pending binding calls exceed configured limits`. Count the call and its bytes, then call the binding by rule 8 in a new task; a missing function of a retained worker fails with `binding is unavailable in this evaluation; reacquire the current tool`. A returned `ptc-image` is registered under a fresh UUID in the worker's image table and encoded as an image token; a result that is not lossless JSON fails with `binding resolution must be lossless JSON`. A failure replies with its message. When the evaluation settled while the binding ran, the reply is the error `PTC evaluation ended before the binding completed` whatever the binding returned. Uncount in every case.
100. `initialized()`. Without a ready process, an active evaluation and a pending initialization: protocol failure `unexpected environment initialization acknowledgement`. For a settled or cancelled evaluation: error reply `PTC evaluation ended before initialization completed`. Otherwise clear the pending initialization and reply with `null`.
101. `run` is the request `[cwd, boot data]` with `code` the erased program, `programFormat`, `retainsState`, `initialization` while one is pending, `maxOutputBytes`, `discardCompletion` and one entry per namespace (`global`, `names` in order, `errorClass` when declared). Its reply is ignored for a settled evaluation. Otherwise it is read by `readProgramResult` (`protocol.ts:91-104`): not an object, `invalid program result`; a malformed `error` or an unknown kind, `invalid terminal error`; both protocol failures; a `value` that does not decode gives the failure `invalid-output` `program completion must be lossless JSON`. A success while an initialization is still pending is the protocol failure `environment initialization completed without Host acceptance`. A valid reply finishes the evaluation only after the bytes already readable on stdout and stderr have been admitted.
102. A protocol failure finishes the evaluation with kind `protocol` and the message with the retained suffix, discards the environment and terminates the process. The cases: a `ready` whose version is not 3, `bootstrap protocol mismatch; upgrade launch.bootstrapPath with the host`; a second `ready` or one without an active evaluation, `duplicate program readiness`; `invalid program log` (not a string, or no ready process and active evaluation); `invalid program image` (unknown id, or the same condition); `idle PTC output limit` (an `outputLimit` under the same condition); the cases of rules 99 to 101; and the framing failures of rule 109 with kind `protocol`. A valid `outputLimit` finishes with `output-limit` `output limit exceeded`, discarding the environment. A channel failure of kind `io` records its message as the control failure, and kinds `io` and `closed` terminate the process when it has not exited.
103. Process exit before settlement: record the outcome, drain stdout and stderr for at most `graceMs`, then, unless the worker closed, finish with `sandbox-unavailable` when the process was confined and `(classify-runner-failure exit-code stderr-tail rules)` matches, else `worker-exit`. The exit message is `Node process exited (<code>, signal <signal>)`, then `: <stderr tail>` when the tail is not empty, then `; control channel failed: <message>` when a control failure was recorded; an absent code or signal prints `null`. A launch failure delivered by the handle finishes the same way, with `(runner-spawn-failure? …)` selecting `sandbox-unavailable` and the failure's message in place of the exit message.
104. Settlement runs at most once per evaluation (`worker.ts:170-201`). Stop the timer and the cancel observation; the deadline covers setup and execution, not cleanup. An `exception` that arrives while an initialization is still pending gets the retained suffix. The outcome is rule 7 when the evaluation overflowed or the failure kind is `output-limit`, `ledger-failure` for any other failure, and `ledger-success` otherwise.
105. The environment is *preserved* when the worker is retained, no initialization is pending, the finish did not ask to discard and the outcome is not `output-limit`. For a timeout or a cancellation of a preserved environment, send the `revoke` notification and wait for the validated reply of the original `run` for at most `stopGraceMs`; anything else (no reply, an invalid reply, a closed channel, disposal of the worker) makes it not preserved. An environment that is not preserved is terminated: mark the worker closed and its cleanup pending, clear the image table, close the control channel, wait for an unfinished start, `subprocess-handle-terminate!`, wait for the handle's `done` and for `subprocess-handle-wait-for-exit`, drain both outputs for at most `graceMs`, close the ports, unregister from the policy processes and clear the pending mark. Termination is shared by concurrent callers and may be retried after a failure. A temporary worker is therefore terminated after every evaluation.
106. For a retained worker and a timeout or cancellation, append `; retained variables were preserved` or `; retained variables were cleared` to the message and compute the outcome again; if it is now `output-limit` and the environment was preserved, terminate it.
107. When the outputs did not both reach their end within the grace, the result is `worker-exit` `managed process exited but its output did not drain cleanly` (also logged at `warning` as `Node process exited but its output did not drain cleanly`). When cleanup raised, the result is `worker-exit` `managed process cleanup failed: <message>` and the worker stays blocked until a release succeeds.
108. Sandbox facts of every result: mode the worker's policy mode, `denied?` false, no enforcement; when the worker's process was confined, enforcement is that of the confined argv and `denied?` is true when the failure kind is not `sandbox-unavailable` and the failure message contains, ignoring case, one of the confined argv's denial signatures. A fresh worker whose evaluation ended at rule 95 has no confined argv, so its facts carry no enforcement, as in dsh.

**Node provider: control channel, wire codec, syntax service, policy invalidation** (R9 "Formats"; `rpc.ts`, `protocol.ts`, `json-wire.ts`, `policy-processes.ts`)

109. Framing (`rpc.ts`). A message is one JSON object in UTF-8 on one line ended by byte 10. The first byte of a message must be `{`, otherwise the endpoint fails with `control message is not a JSON object; the Node bootstrap may be from another release`. An incoming line longer than `maxMessageBytes` fails with `RPC message exceeds <n> bytes`. A write that would raise the bytes queued and not yet written above `maxMessageBytes` fails with `control output exceeds <n> queued bytes`. End of input inside a line fails with `incomplete RPC message`. These have kind `'protocol`. A clean end of input fails with `control channel ended before the program settled` and a closed port with `control channel closed`, both kind `'closed`. A read or write error has kind `'io` and its own message. The failure procedure is called once; after it no method runs, including for lines read in the same chunk, and pending calls of this side are rejected.
110. Methods. Child to host: the notification `ready [version]`; the request `initialized []`; the request `invoke [global, name, wire]`, whose result is a wire token list; the notifications `log [text]`, `image [id]` and `outputLimit []`. Host to child: the request `run [cwd, boot data]`, whose result is a program result; the notification `revoke []`. In syntax mode (rule 115) host to child: the requests `strip [format, source]` and `checkScript [source, filename, lineOffset]`.
111. Envelope rules: a request carries a fresh id string (a decimal counter per endpoint) and gets exactly one reply; a notification carries none. A request for a method that is not in the endpoint's table gets the error reply `[birpc] function "<name>" not found`. An error reply carries only `{message}`: the message of an exception, else its `display` form. There is no timeout at this layer.
112. `(make-rpc-endpoint in out #:max-message-bytes n #:functions table #:on-failure proc) -> rpc-endpoint?`, with `(rpc-call ep method arg ...)` (waits; raises `exn:fail` with the peer's message), `(rpc-notify ep method arg ...)`, `(rpc-close! ep)`, `(rpc-closed? ep)`. `table` maps method names to procedures of the argument list; a procedure may wait and its result, or its raise, is the reply. Reading runs on a plain thread that only posts lines; functions run as tasks.
113. `(encode-ptc-json-wire v #:image [image-token #f])` returns the flat pre-order token list of a lossless jvalue: `'null`, booleans, numbers and strings are their own tokens; a list is `{kind: "array", length: N}` followed by its N values; an object is `{kind: "object", keys: [k…]}` followed by one value per key in order; a `ptc-image` is `(image-token image)`, the image token jobject. Examples: `5` is `[5]`; `{"a": [1, 2]}` is `[{"kind":"object","keys":["a"]},{"kind":"array","length":2},1,2]`.
114. `(decode-ptc-json-wire tokens #:image [decode-image #f])` returns the jvalue or `#f`. It rejects: a value that is not a non-empty list; a marker object with missing or extra keys; a non-string or repeated key; a `length` that is negative or not a safe integer; a count larger than the tokens that remain; an image token when no decoder was given, or with an empty string field or a size that is not a positive integer; a number that is not finite or is `-0.0`; leftover tokens; an unfinished container. The traversal is iterative: depth is chosen by the peer.
115. The syntax service is one long-lived process per provider, started on first use and again after it exits, through the `subprocess` service: argv the resolved executable, the runner path of rule 97 (always this package's runner, never `bootstrapPath`), `<maxMessageBytes>` and `--syntax`; stdin and stdout `'pipe` as the rule 109 channel; stderr `'pipe`, drained and kept as a tail; no control channel; never confined; the environment of rule 97; the cwd the provider's workspace root. It must send `ready [3]` before any request is sent. It evaluates nothing. When the executable cannot be resolved, the process exits, or the channel fails, every waiting request fails with `<detail>`: the resolve failure's message, else the stderr tail, else the channel failure's message. This is how a missing `node` is reported: `code run failed (worker-exit): TypeScript syntax service failed: subprocess-local: command "node" was not found on PATH`.
116. `(strip format source)` returns JavaScript: the request `strip`, whose result is the erased text and whose error reply is the parser's message. `javascript-check-script` is the request `checkScript`, whose result is `null` (giving `#f`) or the error text.
117. Policy processes (`policy-processes.ts`). `(register! policy release)` does nothing and returns a no-op for a policy without a session id; otherwise it records `{session id, mode, release}`, where the mode is the session's current standing mode when `sessions` has that session (`(sandbox-policy-resolve sandboxPolicy #:session session)`) and the policy's mode otherwise, and returns the removal procedure. The `session/event` listener, on a `sandbox/mode` event, marks every record of that session with a different mode as invalidated and starts its release in a new task without waiting; a failed release is logged at `warning` and stays retryable. `(wait session-id)` waits for the releases of that session's invalidated records and raises the first failure. The inverse of the effect `Node PTC policy cleanup` releases every record and waits. A worker registers itself with a release that disposes it; an admitted run registers by rule 88.

**The runner `sidecar/ptc-runner.mjs`** (R9 "H. The Node child"; `ptc-runtime-node/src/process.ts`, `bootstrap.ts`, `environment.ts`, `evaluators/async-function.ts`, `evaluators/repl.ts`, `subprocess/src/control.ts`)

A single ECMAScript module that imports only `node:` built-ins. It is written for this port against the rules below; it is not a copy of the dsh bundle. It needs Node 22.13 or later.

118. `process.argv[2]` is the message limit; not a positive safe integer: throw `invalid control message limit`. `process.argv[3] === "--syntax"` selects syntax mode (rule 131); otherwise program mode.
119. Program mode start. Read and delete `process.env.DSH_SUBPROCESS_CONTROL`; a value other than `pipe`: throw `subprocess control channel was not inherited`. The channel is `new net.Socket({ fd: 7, readable: true, writable: true, allowHalfOpen: true })`. Delete every key of `process.env` whose upper-case form is not `PATH`, `PATHEXT`, `SYSTEMROOT`, `WINDIR`, `TEMP` or `TMP`, then replace `process.env` with an empty null-prototype object and call `syncBuiltinESMExports()`. Wrap `process.emitWarning` so that warnings whose message is `vm.USE_MAIN_CONTEXT_DEFAULT_LOADER is an experimental feature and might change at any time` or `stripTypeScriptTypes is an experimental feature and might change at any time` are dropped.
120. Replace `process.stdout.write` and `process.stderr.write` with a function that pushes the chunk (a string as it is, anything else through `String`) into the active evaluation's log when that evaluation accepts calls, calls the callback (the first function among the next two arguments) with `null` in a microtask, and returns `true`.
121. Create the rule 109 endpoint over the channel with the functions `run` and `revoke`, send `ready [3]`, and serve until the channel fails. On failure set `process.exitCode = 1` when an evaluation is active or the kind is `protocol`, and mark the current evaluation inactive.
122. `run(cwd, data)`. An active evaluation: reject with `overlapping PTC evaluation`. Create the log buffer (rule 126) and the evaluation record `{active: true, reusable: data.retainsState, revoked: false}`, and run the rest inside an `AsyncLocalStorage` store holding it. `process.chdir(cwd)`. On the first evaluation of the process, create the evaluator for `data.programFormat ?? "function-body"` and define on its globals `process` (not enumerable), `inspect` and `Image`, and, for formats other than `function-body`, `console` (the realm's own console).
123. Namespaces (`bootstrap.ts:308-342`). For each declared error class keep one constructor per global, replaced only when the name or member property changes: an `Error` subclass built as `new C(memberName, message)` with own enumerable data properties `name` (the class name) and the member property (the member name). Each namespace is a null-prototype object with one enumerable async function per declared name, defined with `Object.defineProperty`: it takes one argument, snapshots it as lossless JSON (failure: `binding arguments must be lossless JSON`), calls `invoke` with the wire encoding, decodes the reply with the image decoder (failure: `binding resolution must be lossless JSON`) and returns it; every failure is rethrown as the namespace's error class, or a plain `Error` without one, with the message of an `Error` and the `String` of anything else. Define each namespace under its global and each error class under its name on the evaluator globals. Lossless JSON here is: `null`, booleans, strings, finite numbers other than `-0`, dense plain arrays without extra own keys, and plain or null-prototype objects whose own keys are all enumerable strings; `undefined`, functions, symbols, bigints, cycles, sparse arrays and class instances are rejected; a value repeated as a sibling is accepted. The traversal is iterative.
124. With `data.initialization`: evaluate it first; its failure is the run's exception; an overflowed log gives the output-limit result of rule 125; then `await initialized()`; a rejection is the run's exception. An evaluation that was revoked meanwhile finishes with `{}`.
125. Evaluate `data.code` and finish once: `{}` when `data.discardCompletion`; else for the completion value: `undefined` gives `{}`; a value that is not lossless JSON gives `{error: {kind: "invalid-output", message: "program completion must be lossless JSON"}}`; a value whose rule 4 cost exceeds the buffer's remaining bytes gives `{error: {kind: "output-limit", message: "outer output exceeded <maxOutputBytes> bytes"}}`; else `{value: <wire>}`. For a thrown value: the message is `error.stack ?? error.message` for a native error (`util.types.isNativeError`) and `String(value)` otherwise, or `program threw an unrenderable value` when that throws; `{error: {kind: "exception", message}}`, replaced by the output-limit result when the message's string cost exceeds the remaining bytes. Finishing marks the evaluation inactive and, for a reusable process, rejects its pending `invoke` calls with `PTC evaluation ended`.
126. The log buffer (`bootstrap.ts:51-103`) starts at 2 bytes and applies rule 4 arithmetic with one separator byte after the first entry. A push that fits sends `log [text]`. The first push that does not fit sends the rule 5 prefix when it is not empty, then `outputLimit []` once; later pushes are dropped.
127. `inspect(...values)` (`bootstrap.ts:113-163`): a string argument is rendered as it is and any other with `util.inspect(value, { depth: null, maxArrayLength: null, maxStringLength: null })`; the rendered arguments are joined by one space and pushed as one entry ending in a line break; an argument that is a registered image flushes the pending text and sends `image [id]`; images reached while formatting a nested value (through the `util.inspect.custom` hook of `Image`) are sent after that argument's text; a call without arguments pushes a line break; if formatting throws, the text rendered so far is flushed and the error propagates.
128. `Image` is a class whose constructor throws `Images are created by image-producing tools`. Instances are created only by decoding image tokens: frozen objects with own enumerable `attachmentId`, `path`, `width`, `height`, registered in a `WeakMap` from instance to host image id, so a look-alike object is formatted as plain data.
129. The `function-body` evaluator: `new AsyncFunction(...Object.keys(globals), "'use strict';\n" + code)` called with the global values in the main realm; the completion is its return value. All Node globals are visible; modules load with `await import(...)`; there is no `require`.
130. The `repl` evaluator (`evaluators/repl.ts`): `repl.start({ input, output, terminal: false, prompt: "", useGlobal: false, ignoreUndefined: true })` with `_` and `_error` defined as plain writable globals on its context; a program whose trimmed start is `{` is prefixed with `;`; `repl.eval(program + "\n", context, "ptc-repl", callback)` gives the completion or the error; text the REPL writes to its output is, trimmed and when not empty, the active evaluation's exception. For `script` and `scoped-repl` the runner rejects `run` with `ptc-runner: program format "<format>" needs the dsh Node bootstrap; set launch.bootstrapPath`, which the host reports as a `protocol` failure.
131. Ownership and syntax mode. A callback of an ended evaluation cannot log, emit images or start bindings. In a temporary process a binding call that is late or unfinished never settles; in a reusable one it is rejected with `PTC evaluation ended`. `revoke` marks the active evaluation revoked and rejects its pending `invoke` calls with `PTC evaluation canceled`; later binding calls of that evaluation are rejected with `PTC evaluation ended`, the program's `catch` and `finally` blocks run, and `run` then replies `{}`. Syntax mode serves the rule 109 channel over `process.stdin` and `process.stdout`, sends `ready [3]`, and exits when stdin ends. `strip(format, source)`: for `function-body` erase `"async function __dsh_program__() {\n" + source + "\n}"` with `stripTypeScriptTypes` of `node:module` and return the result without the first 35 and the last 2 characters; for other formats erase `source` itself; a parser error rejects with its `message`. `checkScript(source, filename, lineOffset)` constructs `new vm.Script(source, { filename, lineOffset })` without running it and returns `null`, or `String(error)`. When `stripTypeScriptTypes` is not a function the runner writes `ptc-runner: Node.js 22.13 or later is required (node:module.stripTypeScriptTypes is unavailable)` to stderr and exits with code 1 before `ready`.

**The Racket-native provider `racket:ptc-runtime-racket`** (extension; R9 "Hosting PTC natively in Racket"; R20 "racket/sandbox")

132. Facts: language `racket`; isolation `sandbox-evaluator`; program format `'script`; it retains no state; `ptc-runtime-sandbox-mode` is `#f`, because a program has no file, network or process access to confine and every effect is a tool call with its own policy; `ptc-runtime-timeout` is `(ptc-timeout (min timeoutMs maxTimeoutMs) maxTimeoutMs)`. Execution instructions, verbatim: `The program is a sequence of Racket forms in a restricted language: definitions and expressions, with no require, no macro definitions and no file, network or process access. Every effect goes through a tool binding. The whole program is read and checked before any of it runs. The value of the last form is discarded; use (inspect value ...) or displayln to produce output. Each call starts from a fresh environment; nothing persists between calls.` Consequences in the executor: `run_code` offers `timeoutMs` and no escalation parameters, runs without the admission of rule 77, and passes the agent as state owner, which this provider ignores.
133. Load: each of the six config values must be positive and finite (`racket:ptc-runtime-racket: <key> must be positive and finite`); `timeoutMs`, `maxTimeoutMs` and `stopGraceMs` at most 2147483647 (`racket:ptc-runtime-racket: <key> exceeds the supported timer range`); `maxOutputBytes` a safe integer of at least 4, `maxMemoryMb` and `maxPendingCalls` safe integers (`racket:ptc-runtime-racket: <key> must be an integer`, with ` of at least 4` for the first).
134. `ptc-runtime-resolve`: after disposal `racket:ptc-runtime-racket: resolve after disposal`; a request with a sandbox policy raises `racket:ptc-runtime-racket: a sandbox policy is not supported`; the cwd is the request's, else the harness process's current directory, and must be absolute (`racket:ptc-runtime-racket: cwd must be absolute`); the deadline is as in rule 87 with the name `racket:ptc-runtime-racket: timeoutMs`. `ptc-runtime-run` validates the bindings with `(validate-ptc-bindings bindings "racket:ptc-runtime-racket")`; in addition a global or function name whose `tools.name` symbol cannot be written and read back, and two bindings that give the same identifier, raise `racket:ptc-runtime-racket: binding <JSON global>.<JSON name> has no usable identifier`.
135. Reading. The program text is read with `read-syntax`, source name `program`, until end of input, with `read-accept-reader`, `read-accept-lang`, `read-accept-compiled` and `read-accept-graph` all `#f`. The result is a list of syntax objects: the program is data from here on. A read error finishes the run with `exception` and the reader's message; no evaluator is created.
136. Wrapping. The host builds the datum `(module ptc-program <language module path> (#:bindings <spec> ...) (#:completion <keep or discard>) <form> ...)`. A spec is `[<id> <global> <name> <shape> (<required key> ...) (<optional key> ...) <open?>]`: `<id>` is the symbol `<global>.<name>`; `<shape>` is `keywords` when the binding is a `ptc-binding` whose schema has parameters of `type: "object"`, and `positional` otherwise; the key lists come from that schema's `properties` and `required`, and `<open?>` is true unless its `additionalProperties` is `false`. Each namespace with an error class adds `[#:error <global> <Name>? <Name>-<member>]`. The language's `#%module-begin` consumes the two header forms, which a program cannot forge because the host always places its own first, and produces a module that defines and exports one procedure `main` of no arguments whose body is the program's forms in an internal-definition context, followed by `(void)` under `discard`. Inside that body every `<id>` is bound as syntax (rule 137) and the two error-class names as variables (rule 142).
137. A tool identifier is a macro generated from the spec, which is what "bound as a procedure generated from its tool definition" means here. In operator position with shape `keywords`, `(<id> #:k e ...)` is checked at expansion time: a positional argument is the syntax error `<id>: arguments are keywords`; a repeated keyword `<id>: duplicate argument #:<k>`; a keyword that is neither required nor optional, unless the binding is open, `<id>: unknown argument #:<k>`; a required key that is absent `<id>: missing required argument #:<k>`. It expands to `(#%plain-app call-binding '<global> '<name> (#%plain-app list (#%plain-app cons '<key string> e) ...))`, keys in written order. With shape `positional`, `(<id> e)` expands to `(#%plain-app call-binding '<global> '<name> e)` and any other argument count is the syntax error `<id>: expects one argument`. Anywhere else the identifier expands to a procedure of one argument (a hash of arguments, or the positional value) that makes the same `call-binding` application. `call-binding` is a private export of the language that a program cannot name.
138. Analysis. In the evaluator's context the host expands the module with `expand` and walks the fully expanded syntax (the grammar of fully expanded programs, with `kernel-syntax-case`), collecting every application `(#%plain-app f (quote g) (quote n) . rest)` whose `f` is an identifier that `identifier-binding` resolves to `call-binding` of the language module. `(struct program-analysis (bindings forms) #:transparent)` holds the distinct `(cons global name)` pairs in first-occurrence order and the read forms. This is the complete set of bindings the program can ever call, because the language has no other way to reach a binding (rule 139). A pair that was not declared for this run finishes with `exception` `program references an undeclared binding <global>.<name>`. A syntax error of any kind (an unknown tool is the expander's `<id>: unbound identifier`) finishes with `exception` and the expander's message. Then `(ctx-bail ctx 'racket:ptc/inspect analysis spec)` is dispatched from a host task; a string result finishes with `exception` `program rejected before running: <reason>`. Nothing of the program has been evaluated at this point. `(analyze-racket-program runtime program namespaces) -> program-analysis?` performs rules 135 to 138 without the event and without running, raising `exn:fail` with the same messages.
139. The language `dsh-ptc/racket/lang` exports its own `#%module-begin`; `#%app`, `#%datum` and `#%top` of `racket/base`; `inspect`, `parallel`, `json-null` (the symbol `null`, the jvalue null); `match` and `match-define` of `racket/match`; everything `racket/list`, `racket/string` and `racket/math` export; and the exports of `racket/base` except every name that (a) declares, requires or reflects on a module, (b) defines or binds a macro, (c) evaluates, compiles, expands or loads code, (d) reaches a namespace or a variable reference, (e) creates or controls a thread, custodian, security guard, code inspector, plumber or exit, or (f) starts with `#%`. Concretely the excluded names are those that start with `namespace-`, `module-`, `variable-reference`, `syntax-local-`, `current-` (other than `current-seconds`, `current-milliseconds`, `current-inexact-milliseconds`), `load`, `expand`, `compile`, `eval`, `dynamic-`, `thread`, `custodian-`, `make-custodian`, `kill-`, `break-`, `exit`, `#%`, and the names `require`, `provide`, `module`, `module*`, `module+`, `define-syntax`, `define-syntaxes`, `define-for-syntax`, `define-values-for-syntax`, `begin-for-syntax`, `let-syntax`, `letrec-syntax`, `let-syntaxes`, `letrec-syntaxes`, `letrec-syntaxes+values`, `define-syntax-rule`, `make-base-namespace`, `make-base-empty-namespace`, `make-empty-namespace`, `make-security-guard`, `make-inspector`, `make-sibling-inspector`, `make-plumber`. A test expands one module per excluded name and requires each to be unbound.
140. Evaluation. One evaluator per run, made with `(make-evaluator 'racket/base #:allow-for-require (list <language module path>))` under `sandbox-memory-limit` `maxMemoryMb`, `sandbox-eval-limits` `#f` (the deadline of rule 144 must include tool waits, which the sandbox's own timer cannot), `sandbox-namespace-specs` extended with the language module so that its instance is shared with the host, `sandbox-input` `#f`, and `sandbox-output` and `sandbox-error-output` set to output ports that post their bytes to the run's owner task. The default path permissions and network guard stay, so file, network and process access are denied by the sandbox as well as absent from the language. Every call into the evaluator is made from a plain thread under `blocking`, never from a task. After analysis the host evaluates the *unexpanded* module form in the evaluator and then calls `((dynamic-require ''ptc-program 'main))` with the language's `current-run` parameter set to the run's record. The expanded syntax is used for inspection only: syntax expanded under the sandbox's code inspector is refused by `compile` (`cannot use identifier tainted by macro transformation`), which was observed on Racket 9.3. The evaluator is killed with `kill-evaluator` when the run settles.
141. A binding call runs on a program thread: `call-binding` converts the arguments, posts `(global name arguments reply)` to the run's owner task and blocks on the reply channel. The owner replies with an error when the evaluation has settled (`PTC evaluation ended`) or `maxPendingCalls` calls are pending (`pending binding calls exceed configured limits`); otherwise it calls the binding by rule 8 in a new task and replies with the converted result, or with the failure's message. Program values to jvalues: a string, a boolean, `'null`, an exact integer, a finite flonum other than `-0.0`, an exact rational (as a flonum), a list (array), an immutable or mutable hash with symbol or string keys (an object; keys of the keyword form in written order, keys of a hash in the order `cordis-data` reads hashes); anything else fails the call with `binding arguments must be lossless JSON`. Jvalues to program values: a jobject becomes an immutable `hasheq` with symbol keys, a list stays a list, a `ptc-image` becomes the hash of `attachmentId`, `path`, `width` and `height`; scalars are unchanged.
142. A failed call raises, in the program, an `exn:fail:ptc-binding` (a struct of the language module with the fields `class` and `member`) whose message is the failure message, or a plain `exn:fail` for a namespace without an error class. For the error class `(ptc-error-class "ToolCallError" "toolName")` the program has `ToolCallError?`, true for such an exception of that class, and `ToolCallError-toolName`, its member name. `(parallel thunk ...)` runs each thunk in its own thread of the evaluator, waits for all, and returns the results in argument order, or re-raises the first raise in argument order.
143. Output. `(inspect v ...)` renders each argument (a string as it is; a value that rule 141 can convert as `jvalue->string` with `#:indent 2`, object keys in `js-string<?` order; anything else with `~s`), joins them with one space, appends a line break and posts one text entry; without arguments it posts a line break. Bytes written to the standard output and error ports are decoded by rule 94 and posted as text entries. The owner admits entries to a ledger of `maxOutputBytes` with rules 6 and 7; the first entry that does not fit finishes with `output-limit` `output limit exceeded`.
144. Deadline and cancellation. The timer and the cancel event finish the evaluation with the kinds and messages of rules 92 and 93 in their non-retained forms; the phase is `before code started` until `main` is called. To stop a program the owner calls `break-evaluator`, so handlers and `dynamic-wind` post thunks run, waits for the evaluation to end for at most `stopGraceMs`, and then kills the evaluator. A synchronous loop is interrupted this way, which the Node provider can only do by killing its process.
145. Outcomes. A raise of the program is `exception` with `exn-message` for an exception and the `~s` form for any other value. Under `keep`, `main` returns the last form's value: `(void)` gives no value, a convertible value is the completion, and anything else is `invalid-output` `program completion must be lossless JSON`. An evaluator that terminated on its own is `worker-exit` `Racket evaluator terminated: <reason>` (`out-of-memory` for the memory limit). Results carry no sandbox facts. The kinds `protocol` and `sandbox-unavailable` are never produced.
146. Disposal cancels every live run with the string `runtime disposed`, kills its evaluator and waits. `ptc-runtime-release!` does nothing and initializer registration is unsupported (the fallbacks).

## Racket design notes

- **Descriptor 7.** dsh's Node child talks to its host over an inherited duplex pipe at file descriptor 7; stdout and stderr are raw program output, and they cannot carry control traffic because processes the program starts write to them directly. Racket's `subprocess` passes exactly three descriptors. Three solutions were considered. Framing the protocol on stdin and stdout would need the program's own stdout moved elsewhere, and Node cannot re-point descriptor 1 for its grandchildren without a native addon. A Unix-domain socket named in argv would change the child's launch contract and need a path that every sandbox profile lets the child reach. The chosen solution is the control channel of the `subprocess` service (`dsh-exec` rule 28: a loopback socket connected by a bash trampoline before the real argv is exec'ed, authenticated by a one-time token, and left open on descriptor 7 with `DSH_SUBPROCESS_CONTROL=pipe`). This package requests it with `control?` and never implements a transport. The child therefore sees what it sees under dsh, the runner adopts the descriptor with the same four lines as `openInheritedControlChannel`, a sandbox runner between the trampoline and Node only has to keep an already connected descriptor open, and a dsh-built bootstrap can be dropped in through `launch.bootstrapPath`. The Python provider reuses the same channel and moves it to descriptor 3 inside the interpreter with `os.dup2`, so the dsh bootstrap is unchanged.
- **Type erasure in a syntax service.** In dsh the harness process itself calls `stripTypeScriptTypes` before any child exists. This port has no JavaScript engine in the harness process. Erasing inside the program child was rejected: a syntax error would start a confined process (dsh starts none, and its result then carries no enforcement fact, which is model-visible in `File sandbox: <mode>.`), an initializer could not be validated at registration, and the `run` message would stop being revision 3, so a dsh bootstrap could not serve the formats this port does not implement. A second mode of the same runner, long-lived, unconfined and evaluating nothing, keeps every rule of the evaluation machine as dsh states it and costs about 0.3 ms per program after the first (about 36 ms once, measured with Node 22.23 on this machine).
- **A runner written for the port.** ADR 0009 forbids depending on a dsh build, so `ptc-runner.mjs` is a new file of a few hundred lines against rules 118 to 131. It implements the two evaluators that need nothing but Node built-ins. The `script` and `scoped-repl` evaluators parse programs with acorn; this port does not vendor a parser, and marks them wrapped.
- **One owner task per worker and per run.** The TypeScript relies on one event loop and guards every callback with `settled` checks. Here a worker's state machine and a run's sub-dispatch driver are each one task reading a mailbox; reader threads, timers and cancel events only post. Settlement happens once because one task performs it, and the kernel's baton gives the run-to-completion steps the rules assume.
- **Generics for the two seams.** `gen:ptc-runtime` has three providers and `gen:workflow-engine` one, with room for a second engine. The optional members of the dsh abstract class are fallback methods. `gen:javascript-syntax` is a second interface on the Node provider's value, not a method of the seam, because only a JavaScript-hosting provider can implement it.
- **Bindings are applicable structs.** `ptc-binding` carries the tool schema beside the procedure. The Node and Python providers ignore it; the Racket-native provider generates its tool macros from it. dsh's runtime seam is deliberately ignorant of tools, and stays so: the schema is opaque data to the seam.
- **Projection instead of property getters.** dsh installs getters on the transport definition so that `description` and `parameters` follow the mounted runtime. A `tool-definition` is immutable here; the executor computes the schema in `tool-executor-describe` (rule 14). The static spec that validates arguments is unchanged.
- **Immutable jvalues.** dsh snapshots binding arguments twice so that a tool mutating its arguments cannot change the logged copy, deep-freezes schemas and clones `args`. None of that has a counterpart.
- **Payloads other packages read are hashes and jobjects.** The dispatch log and the `workflow/*` infos are read by `dsh-fs` and by any recorder without requiring this package.
- **`workflow-start` may wait.** dsh validates synchronously because `node:vm` is in its process. Here the parse check is a request to the syntax service, so the procedure may wait before it publishes; the order of observable steps (validate everything, then `workflow/start`, then the body) is unchanged.
- **The guest is data.** The workflow guest is a self-contained module that imports only `node:vm`; dsh itself transports it as text in a `data:` URL. Shipping that text is not a build dependency on dsh, and reimplementing 600 lines of script-facing semantics in a second JavaScript file would only add a way to differ.
- **Late binding to siblings.** `jobs` is reached through a port this package owns, as `dsh-exec` does for its sibling services. `subagents` is reached through `private/siblings.rkt`, which looks up the documented procedures of `dsh-subagent/subagents` and `dsh-subagent/types` with `dynamic-require` when the workflow plugin mounts and fails that mount with a message naming the missing module; the injected `subagents` service guarantees the module is loaded in every real composition.
- **Text that Racket cannot hold.** A Racket string has no lone surrogates. JSON from a child that escapes one is read as U+FFFD by `cordis-data`, and the byte meter then charges 3 bytes where dsh charges 6. No rule depends on the difference except exact-limit tests with such input, which are not mirrored.
- **Where code as data pays off: the Racket-native provider.** The JavaScript path treats the model's program as an opaque string handed to a hostile peer: the harness learns what a program does one tool call at a time, after the earlier calls have had their effects, and it protects itself with a process boundary, an environment scrub, a wire codec and an operating-system sandbox. In the native provider the program is a term. `read-syntax` yields syntax objects, a module language fixes the complete set of bindings a program can mention, and `expand` resolves every identifier. Three things follow that the string path cannot offer. First, the set of tools a program can call is exact and known before any effect (rule 138), because the language has no computed lookup, no `eval`, no `require` and no macro definitions; for JavaScript the same question is undecidable in practice (`tools[name]`, `globalThis`, `import()`). A guard can therefore refuse a whole program up front through `racket:ptc/inspect`, where the JavaScript path can only deny one sub-call after its predecessors ran. Second, each tool is a macro generated from its schema, so a misspelled or missing argument is a syntax error that costs no tool call, where the JavaScript path dispatches, fails in the pipeline and logs a failed sub-call in the middle of a half-executed program. Third, authority is the export list: there is no ambient capability to fence, hence no escalation parameters, no admission bookkeeping, no protocol and no failure kinds for a peer that misbehaves.
- **What the native provider cannot be compatible with.** It cannot run a program a dsh session recorded, because those are TypeScript or Python. It cannot offer the dsh `run_code` contract: the description, the SDK section, `inspect` as `util.inspect`, `Image` values, Node and Python library access, direct file access under the session's file policy (the `ptc-node-read-only` and `ptc-node-workspace` behaviours), retained environments, environment initializers and one-execution escalation all assume a general-purpose runtime in a confined process. It cannot serve the workflow engine, which needs a JavaScript host for the guest. Its prompt text differs from every recorded header class, so no committed snapshot applies to it. A log written with it is still a valid dsh log (the event types are the same), but dsh cannot re-run its programs. In-process isolation rests on the sandbox library, the security guard and custodian memory accounting, which is checked at collections; it is weaker than a process boundary against a fault in the runtime itself. For these reasons it is selected only by a configuration row that names `racket:ptc-runtime-racket`, and no profile of this port does.
- **Macros.** This package adds no declaration macro to the harness. It uses `define-session-event` for its six event types. The only macros it introduces belong to the program language: its `#%module-begin`, which removes the possibility of a program escaping the wrapper or reaching a binding without a visible reference, and the per-tool transformer, which removes the class of failures "wrong argument name or missing argument discovered after earlier effects".
- **Racket-only additions**, for the coordinator's ADR list. Names in the `racket:` namespace: the plugin `racket:ptc-runtime-racket` and the event `racket:ptc/inspect`. Further additions: the language id `racket` with its `run_code` flavor and the module `dsh-ptc/sdk-rkt`; the modules `dsh-ptc/racket` and `dsh-ptc/racket/lang` with `analyze-racket-program` and `program-analysis`; the schema field of `ptc-binding`; `gen:javascript-syntax`; the syntax service with the runner's `--syntax` mode and its methods `strip` and `checkScript`; the launch default `node` and the load failure for `launch.kind: "embedded"`; the load warning and the run failure for formats the shipped runner does not implement; `gen:workflow-job-port`; `make-workflow-run` and `workflow-emit` as exported procedures; the test doubles of `dsh-ptc/testing`; the two loader lines of the Python launch; registration of the two dispatch event declarations by the executor plugin. No `x-racket` configuration key is added, and nothing here changes what an unmodified dsh configuration writes to a session log.

## Work units

The package is split into three units. The interface between them is the set of public module exports listed in this document.

| Unit | Modules | Depends on |
|---|---|---|
| A: seam, data plane, executor | `ports`, `runtime`, `json`, `output-ledger`, `errors`, `events`, `sdk-ts`, `sdk-py`, `sdk-rkt`, `executor`, `run-code`, `testing` (the scripted runtime), `plugin/tool-executor-ptc`, `plugins`, `main` and their tests | wave 3, `dsh-exec` (`sandbox`, `sandbox/policy`, `ports`, `timeout`, `errors`) |
| B: providers | `node`, `node/rpc`, `node/wire`, `sidecar/ptc-runner.mjs`, `python`, `sidecar/py/*`, `racket`, `racket/lang`, `testing` (the scripted peer), the three runtime plugins and their tests | `runtime`, `json`, `output-ledger` of unit A; `dsh-exec/subprocess` |
| C: workflow | `workflow`, `workflow/ptc-engine`, `sidecar/workflow-guest.mjs`, `workflow/tool`, `private/siblings`, the two workflow plugins and their tests | `runtime`, `errors`, `ports`, `testing` of unit A |

Order: unit A first delivers `ports`, `runtime`, `json`, `output-ledger`, `errors` and the scripted runtime of `testing` (about 900 lines); B and C start when those export their signatures, and A's executor is built at the same time. Unit B is tested against the scripted peer without Node and against the real runner when Node is present. Unit C is tested against the scripted runtime, which plays the guest by calling the `workflowHost` bindings, and needs unit B only for the tests that run the real guest. `dsh-ptc/testing` has two owners on purpose: `make-scripted-ptc-runtime` belongs to A and `make-scripted-peer` to B, in separate private modules that `testing` re-exports. If unit B is too large for one implementer, the Python provider (`python`, `private/python-pump`, its plugin and test) is the part to hand to a fourth person: it shares only `runtime` and `output-ledger`.

## Open questions

1. **Dynamic schema of registered program tools.** dsh re-reads the runtime's instructions and sandbox mode whenever a registered program tool's schema is projected. `make-tool` takes fixed values. Recommended default: compute once in `make-run-code-tool` (rule 15); if `dsh-tools` later accepts a procedure for `#:description` and `#:parameters`, pass thunks.
2. **Provider of `gen:workflow-job-port`.** `dsh-automation` has no contract yet. Recommended default: its `jobs` service value implements the port of `dsh-ptc/ports`; a mounted value that does not is treated as absent, with one warning, so background calls fail with the jobs-unavailable message of Tools.
3. **Reaching `subagents`.** ARCHITECTURE.md gives this package no dependency on `dsh-subagent`. Recommended default: `private/siblings.rkt` resolves `subagents-provider`, `subagents-start-activation`, `subagent-activation-child-id`, `subagent-activation-result`, `subagent-activation-dispose!` and the accessors of `subagent-result` with `dynamic-require`. If the coordinator adds `dsh-subagent` to this package's dependencies, that module becomes a plain `require` and nothing else changes.
4. **The control channel inside a sandbox runner.** `dsh-exec` open question 4 covers a runner that hides the loopback interface. The channel is connected before the runner starts, so an already open descriptor is all the runner must preserve. Recommended default: rely on `dsh-exec` rule 28 and add a `node-runner-test.rkt` case under each runner that exists on the test machine.
5. **Wrapped evaluators.** `script` and `scoped-repl` need a JavaScript parser. Recommended default: do not vendor one; require `launch.bootstrapPath` for those modes (rule 85). `persistent-in-memory` therefore needs `replScoped: false` to work with the shipped runner, which differs from dsh's default for that mode; the plugin says so in its load warning.
6. **Session event catalogue.** `dsh-session` checks declared fields on live appends only for registered types. Recommended default: the executor plugin registers its two declarations when `sessions` is present and the tags are free (Plugins); the workflow tool registers its four the same way. A second executor in another scope then relies on the first one's registration.
7. **Unicode identifier tables.** Rule 28 approximates `XID_Start` and `XID_Continue` with general categories. Recommended default: accept the approximation; names that differ are routed to the subscript or `dict[str, Any]` form by one side only, and no shipped tool has a non-ASCII name.
8. **Replay of PTC fixtures before wave 5.** `dsh-test-support` rule 29 excludes fixtures with `run_code`. Recommended default: extend its stand-ins with the scripted runtime of `dsh-ptc/testing`, keyed by program text and fed from the fixture's `tool/ptc-dispatch` rows, so `ptc-turn` replays without Node; the real-runner variant stays a separate test.
9. **Rendered failures of the workflow drive.** dsh reports a JavaScript stack for a host-side raise in the drive. Recommended default: `error->js-string`, one line (rule 166).
10. **Depth of the Python host.** Rules 147 to 156 state the protocol and every message; the TypeScript host has about 1,200 further lines of defensive stream handling. Recommended default: implement the rules with the mailbox design of the Node worker, mirror `runtime.spec.ts`, and treat any interleaving the rules do not decide as `worker-exit` with a message that names the frame.
11. **Memory accounting of the native provider.** `sandbox-memory-limit` is enforced at collections and counts memory reachable only from the evaluator's custodian. Recommended default: keep `maxMemoryMb` at 512 and document that the limit is approximate; values shared with the host (tool results) are charged to the host.
12. **Model-direct errors when the executor is the registered program tool's owner.** A registered program tool has no `reject` procedure, so a nested call to a name outside its private set is an ordinary unknown-tool failure. This is dsh's behaviour and is stated here only so that nobody adds a hint.
