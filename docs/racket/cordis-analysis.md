# Cordis in Racket: analysis

This document studies the Cordis kernel that dsh is built on and decides how each of its ideas is expressed in Racket. The Racket kernel under `racket/cordis/` is built from this document, so it is kept current: when the implementation teaches us something, the text here changes first.

## 1. Sources

- The vendored kernel: `vendor/cordis/src/{context,fiber,events,registry,reflect,service,utils,logger}.ts` at Cordis 4.0.0-rc.11, with the local modifications logged in `vendor/README.md` (V6 lifecycle hardening, V15 configuration access, V22 volatile config, V25 loader lifecycle).
- The loader stack: `vendor/{loader,include,group,hmr,timer,schemastery,cosmokit}`.
- The paper: Shi, Zhang, Cui, *A Programming Paradigm for Spatiotemporal Composability*, arXiv:2608.25512. Section numbers below refer to it. A full digest is in [recon/19-paper-digest.md](recon/19-paper-digest.md).
- The dsh primer, `docs/cordis-primer.md`, and the kernel-level specs under `scripts/cordis-*.spec.ts`.
- Reconnaissance notes [recon/01-cordis-core.md](recon/01-cordis-core.md), [recon/02-cordis-loader.md](recon/02-cordis-loader.md) and [recon/20-racket-mechanisms.md](recon/20-racket-mechanisms.md).

## 2. What Cordis claims

The paper separates dynamic composition into two independent problems.

**Temporal composability** is the ability to remove a component and have every side effect it installed disappear. The paper's answer is the *revertible effect*: every operation that changes the context returns its own inverse, and the runtime, not the component author, holds the inverses and runs them. A composite effect needs no hand-written inverse because the inverse of a sequence is the reversed sequence of inverses.

**Spatial composability** is the ability of a component to say what it needs from other components and to be started, stopped and restarted as those needs become satisfied or unsatisfied. The paper's answer is the *reactive coeffect*: a component carries a specification of the context it requires (its `inject` list), and every change to the context is classified against that specification to decide whether the component activates, deactivates, or is unaffected.

The **context paradigm** joins the two. One first-class object, the context, is the only way to perform an effect and the only way to read a coeffect. Because every operation goes through a context, every operation is attributable to the component that owns that context. The paper states the consequence as a set of theorems over a small calculus of components: lifecycle transitions preserve well-formedness, unloading a component restores the context up to an observational equivalence, a provider's bindings stay readable to its dependents for their whole teardown (the coeffect ordering result), every reachable state can make progress, and interleavings of independent components converge.

A **component** is a pair of a coeffect specification and an effect function. A **fiber** is one instantiation of a component on a context: it has an identity, a parent, the committed view of its dependencies, the accumulated inverse of everything it has done, and a lifecycle state.

Section 6.4 of the paper lists what a host language must supply. For the temporal side: closures, so an inverse can capture the state it restores, and a way to introduce and retract code at run time. For the spatial side: a way to declare dependencies, a way to type them, and a way to mediate access to them, which in TypeScript is a `Proxy` and which the paper notes can instead be generated by compile-time metaprogramming. Section 6.7 asks what a language co-designed with the paradigm could add: an implicit context instead of a threaded argument, effect iteration compiled into a state machine, and dependency specifications visible to the compiler. Racket supplies the minimum directly and can reach most of the co-design list with parameters, generators and macros. That is the reason this port is interesting.

## 3. The vendored kernel as built

This section states the behaviour the Racket kernel has to reproduce. It is written from the TypeScript source.

### 3.1 Context

A `Context` is an object in a prototype chain. The root context owns the four kernel services (`reflect`, `registry`, `events`, `logger`) and the root fiber. `ctx.extend(meta)` makes a child whose prototype is the parent; a plugin fiber's context is `parent.extend({ fiber })`. Two tables are inherited the same way:

- `ctx[isolate]` maps a service name to a realm symbol. `ctx.isolate(name, label?)` returns a child context in which `name` resolves to a different realm. Two contexts that map a name to different realms see independent services.
- `ctx[intercept]` maps a service name to configuration that the provider consults when the service is used from this context. `ctx.intercept(name, config)` layers a new entry; a service merges the layers from outermost to innermost.

Neither derivation needs an inverse: dropping the child context undoes it.

### 3.2 Effects

`ctx.effect(callback, label)` is the only mutation primitive. It asserts that the owning fiber is alive and not unloading, registers a disposer wrapper in the fiber's disposable list *before* running the callback (so an unload that begins inside the callback still finds it), then runs the callback. The callback may return:

- nothing;
- one disposer function;
- an iterable of disposers (a generator that `yield`s one inverse per step);
- a promise of a disposer;
- an async iterable of disposers.

The returned disposer is single-shot and idempotent. It runs the collected inverses in reverse order, awaiting each asynchronous one before starting the next. Disposing an effect whose setup is still running waits for setup to finish and then reverts it. A synchronous setup failure rolls back whatever was collected and rethrows. A disposer yielded by a child effect is moved out of the fiber's list into the parent effect's own list, which is what makes effects nest: the inverse of a child effect is itself an effect on its parent.

The paper's Algorithm 1 is the same thing with one more detail that matters for the port: an effect iterator is consulted at each step boundary, and a guard that has tripped stops the iteration with only the inverses accumulated so far.

### 3.3 Services

`ctx.provide(name, value, check?)` is an effect. It declares `name` as a service property, assigns the name a root realm if it has none, and installs an `Impl` record `{uid, name, value, ctx, check, isolate, dependents}` in the store under the realm that `name` resolves to in the providing context. A second provider in the same realm is an error. Its inverse removes the record, notifies dependents, and then waits until no fiber still depends on the record before it lets go of it.

`ctx.get(name, strict = true)` is the reflective read: realm lookup, then store lookup, returning `undefined` when absent or, in strict mode, when the provider's fiber is not `ACTIVE`. It never throws.

`ctx.<name>` is the checked read, implemented by a `Proxy`. It walks from the accessing fiber up the parent chain. At each fiber, a binding in the fiber's *committed view* (or among the fiber's own provisions in the right realm) authorizes the access. A fiber that declares `name` in `inject` without having committed it means the access comes from an inactive context and fails. Reaching the root without any declaration fails with `cannot get property "<name>" without inject`. The walk also stops with that error when it would cross into a parent that resolves the name to a different realm. This is the paper's Algorithm 6.

`ctx.set(name, value)` replaces the value of an existing `Impl` in place, only from the fiber that provided it. In-place replacement is deliberately invisible to dependents; a provider that wants dependents to reload withdraws and provides again.

`ctx.accessor` and `ctx.mixin` add computed properties to every context; this is how `ctx.on`, `ctx.plugin` and `ctx.effect` appear as methods of a context although they belong to kernel services.

### 3.4 Use site and definition site

When a plugin calls `ctx.tools.register(...)`, the method runs with `this.ctx` bound to the *caller's* context, not the provider's. Cordis does this with a second layer of proxies (`getTraceable`, the `tracker` and `shadow` symbols). The effect is that a service method that registers something on behalf of a caller attaches the registration to the caller's fiber, so it is reverted when the caller unloads. At the same time, service lookups made inside that method resolve against the *provider's* declared injections, because the provider's code can only rely on what the provider declared. The kernel therefore tracks two contexts per call: the definition site, which governs dependency resolution, and the use site, which governs effect ownership, isolation and interception.

### 3.5 Plugins and fibers

`ctx.plugin(plugin, config)` accepts a function, an object with `apply`, or a class. It finds or creates the runtime record for the callback (name, config schema, list of fibers) and always creates a new fiber. A plugin may carry `name`, `inject`, `Config` and `provide`. `inject` is a list of names or a map from name to interception config; entries may be optional at the loader level.

A fiber is created as an effect of its parent fiber, so unloading a parent cascades to its children. It then publishes `internal/plugin` and computes its *target*.

The lifecycle follows the paper's Algorithm 5. The states are `PENDING`, `LOADING`, `ACTIVE`, `UNLOADING`, `FAILED` and `DISPOSED`.

- The **target** (called `epoch` in the source) is either `INACTIVE` or a string made from the fiber's revision counter and the `uid` of the provider of each injected name. It is `INACTIVE` whenever any injected name has no active provider in the fiber's realm, or its `check` rejects.
- **refresh** recomputes the target. If it changed and no transition is in flight, the fiber starts loading (target became satisfiable) or unloading.
- **reload** snapshots the resolved providers into the committed view, registers the fiber as a dependent of each, yields once, and then runs the plugin: `new callback(ctx, config)` followed by its `[Service.init]()` for a class, or `callback(ctx, config)` for a function. The result is treated as an effect. On completion, if the target is unchanged the fiber is `ACTIVE`; otherwise it chains into unload. A thrown error is logged, recorded on the fiber, and the fiber becomes `FAILED`; only `update()` clears a failure.
- **unload** first waits until no fiber depends on any of this fiber's provisions, then disposes all of the fiber's effects, starting them in reverse registration order, then releases its hold on its own providers. If the target has meanwhile become satisfiable again it chains into reload.
- Transitions are **inertial**: once started, a reload or unload runs to completion before the fiber reacts to a newer target. `fiber.inertia` is the handle of the transition in flight and `await fiber` waits until there is none, then throws the recorded error if the fiber failed.
- A provider that leaves `ACTIVE` stops counting as a provider at once, before any of its inverses run. Its dependents therefore see an unsatisfied target and begin their own teardown while the provider's bindings are still in place. This is what the paper's coeffect-ordering theorem rests on.
- `fiber.restart()` bumps the revision, which changes the target and forces unload then reload. `fiber.update(config)` validates the new config, publishes `internal/commit`, and runs the `internal/update` waterfall whose innermost step is a restart; a listener may handle the update without restarting.
- `fiber.dispose()` clears the uid, notifies `internal/plugin`, forces the target to `INACTIVE`, and waits for the unload.

### 3.6 Events

Listeners are stored per event name with the context that registered them. `ctx.on(name, listener, { prepend, global })` is an effect; `prepend` puts the listener first. Before registering, `on` offers the registration to `internal/listener` through `bail`, which lets a service claim certain event names.

There are five dispatch modes, and an event is meant to be dispatched in exactly one of them:

| Mode | Behaviour |
|---|---|
| `emit` | call every listener in order, synchronously; no result |
| `parallel` | start every listener, wait for all, raise an aggregate error if any failed |
| `serial` | await listeners one by one; return the first result that is not `null`, `undefined` or `false` |
| `bail` | like `serial` but synchronous |
| `waterfall` | around-middleware: each listener receives the arguments and `next`; calling `next()` runs the rest of the chain and returns its result; not calling it short-circuits; calling it twice is an error. The last argument of the dispatch is the innermost function. |

A dispatch may carry a `this` argument with a filter, which restricts delivery to listeners whose context passes the filter; `internal/service` uses this to deliver only within the affected realm.

Kernel events: `internal/plugin`, `internal/status`, `internal/service`, `internal/update`, `internal/commit`, `internal/config`, `internal/get`, `internal/set`, `internal/listener`, `internal/dispatch`.

### 3.7 What is JavaScript and what is Cordis

Several mechanisms in the source exist only because of the host language:

- `Proxy` and prototype chains implement property-style service access, the use-site and definition-site split, and context inheritance.
- Promises and microtask order implement asynchronous effects and the scheduling of transitions.
- `Symbol.for('cordis.*')` keys implement protocols between the kernel and service classes.
- Declaration merging gives event names and service keys static types.
- Stack-trace surgery (`composeError`) makes an error thrown inside an effect point at the registration site.

The Racket kernel reproduces the behaviour of sections 3.1 to 3.6 and replaces every mechanism in this list.

## 4. Mapping to Racket

Each subsection names the Cordis concept, the Racket mechanism chosen, the alternatives, and the reason. Decisions with lasting consequences have their own ADR.

### 4.1 Contexts and scopes

**Chosen:** a context is an immutable struct `(context root parent fiber realms intercepts meta)`. `realms` and `intercepts` are persistent hashes, so `context-isolate` and `context-intercept` are functional updates that share structure with the parent, which is exactly what prototype inheritance gave. The mutable kernel state (service store, listener table, runtime registry, property table, scheduler) hangs off the root, reached through `context-root`.

A parameter, `current-context`, carries the context implicitly. The kernel sets it whenever it runs plugin code: the plugin body, listeners, disposers and tasks. Threads inherit the parameterization of their creator, so a task spawned by a plugin starts in that plugin's context.

**Alternatives:**

- *Parameters only* (no explicit argument). This is the paper's section 6.7 ideal of an implicit context. It fails in one specific way in Racket: a closure does not capture the parameterization it was created in, so a callback stored by one component and called later by another runs with the caller's context. That is the use site, which is right for service methods and wrong for a listener that wants to register something in its own plugin.
- *Explicit argument only*. Unambiguous and what Scheme programmers expect, but every helper has to thread the context.
- *Units* (`racket/unit`) as scopes. A unit's imports are fixed when it is invoked; there is no notion of a derived scope that shadows one binding.

**Reason:** the two notions Cordis reconstructs with proxies are the two binding disciplines Scheme already distinguishes. The *definition site* is lexical scope: a plugin body closes over its own context and its injected services. The *use site* is dynamic scope: `current-context` during a call is the caller's context. So the rule in the Racket kernel is: kernel operations take the context as their first argument; a service procedure that acts on behalf of its caller takes `#:ctx [ctx (current-context)]`; a plugin's own registrations use the lexically bound `ctx`. No proxy is needed, and the reader can see which context is meant. See [ADR 0003](../adr/0003-explicit-context-with-parameter-default.md).

### 4.2 Revertible effects

**Chosen:** `(ctx-effect ctx thunk #:label label)` with the same contract as section 3.2. A disposer is a struct with `prop:procedure`, so it can be called, and it remembers its label, its children and the source location of the call that created it. The thunk may return `(void)`, a disposer or any procedure of no arguments, a list of those, a *generator* that yields them, or an *awaitable* (section 4.6) that produces any of the above. The fiber's accumulator is a LIFO list.

Effect iterators are Racket generators (`racket/generator`), which are implemented with continuations. A generator is the direct counterpart of the paper's effect iterator: the kernel resumes it one step at a time and can stop at a step boundary, keeping the inverses yielded so far, when the fiber's target has changed.

The `effect` macro wraps the common case and captures the source location of the use for the label, which replaces the stack surgery that the TypeScript kernel does at run time.

**Alternatives and how they relate:**

- `dynamic-wind` pairs an action with an inverse, but its scope is a dynamic extent: the post thunk runs when control leaves the body. A plugin's effects must outlive the call that installs them and be reverted later by someone else. `dynamic-wind` is the right tool *inside* one component for local resources, and the paper says the same of RAII (section 7.3, "statically scoped reversal").
- Custodians reclaim resources without being told the inverse. This is the paper's fourth family, "interposed reclamation": the platform records acquisitions at an interface it controls. It is complementary; see section 4.3.
- Software transactional memory and undo logs revert only what the platform knows how to log.

**Reason:** closures as inverses, collected by the runtime, is the paper's model and needs nothing more than `lambda`.

### 4.3 Automatic cleanup when a plugin unloads: custodians

**Chosen:** every fiber owns a custodian, created as a child of its parent fiber's custodian. Plugin code runs with `current-custodian` set to it. Unload is two phases: first the revertible effects run in LIFO order, as in Cordis; then the fiber's custodian is shut down and replaced with a fresh one for the next activation.

This is the largest place where Racket adds to the design. A Cordis effect is only reverted if the author returned an inverse. The paper is explicit that this is an obligation on the author that the runtime cannot check (section 5.1.1), and its motivating study of plugin systems is about forgotten cleanups. A custodian closes that gap for everything the Racket runtime manages: threads, ports, TCP listeners and connections, subprocesses, timers built on threads, and anything registered through `ffi/unsafe/custodian`. A plugin that forgets to stop its polling thread still loses the thread on unload.

Custodians are not a replacement for inverses, and the analysis should be honest about why:

- A custodian shutdown has no ordering and no semantics. It cannot remove a listener from a table or withdraw a service; those are ordinary data-structure updates that only an inverse can undo.
- It kills threads without unwinding them, so `dynamic-wind` post thunks in a killed thread do not run.
- It is not selective: everything allocated under it goes.

So the inverse list restores the *context*, and the custodian reclaims the *resources*. The custodian tree mirrors the fiber tree, which also gives a per-plugin memory limit through `custodian-limit-memory`, something the Node runtime cannot express without a worker. See [ADR 0004](../adr/0004-custodian-per-fiber.md).

### 4.4 Services and dependency injection

**Chosen:** the store is a mutable hash on the root from realm (an uninterned symbol) to an `impl` struct. `ctx-provide`, `ctx-get`, `ctx-set!` and `ctx-ref` reproduce section 3.3; `ctx-ref` is the checked read of Algorithm 6 and raises `exn:fail:cordis:inject` with the same three distinct messages.

On top of the reflective API sit two macros that carry the dependency declaration into the compiler:

- `define-service` declares a service key together with a contract for its value. It defines a typed accessor and records the key at compile time.
- `define-plugin` takes `#:inject (tools llm [approval #:optional])` and binds each injected service as a lexical variable in the plugin body. Because a fiber reloads whenever one of its providers is replaced, the committed view is constant during one activation, so binding the value once at entry is sound; this is the coeffect-ordering property used as a compiler optimisation. A body that mentions a service it did not declare has an unbound identifier, which is a compile-time error. This is the mediation by compile-time metaprogramming that section 6.4 of the paper anticipates, and the compile-time dependency check that section 5.1.4 says is possible in principle.

Contracts are checked when a value is provided, and blame falls on the provider's module if the value does not meet the service contract, or on the consumer if it misuses a higher-order service. Blame assignment lines up with the provider and consumer roles of a dsh capability seam, which is a better fit than a type error at an arbitrary call site.

**Alternatives:**

- `racket/unit`. A signature is a Service Definition, a unit is a provider or a consumer, and linking is injection. Units check that every import is satisfied before anything runs, which is attractive. But linking is a one-time act: a compound unit cannot have one constituent withdrawn while the rest keep running, and there is no built-in notion of "this import became available later". Using units would mean invoking a fresh unit per activation with imports fed from the store, at which point the unit contributes signature checking and nothing else. The kernel offers `unit->plugin` as an adapter for code that wants signature-checked plugins, and the guide discusses it, but units are not the kernel's model.
- `racket/class` with interfaces. Works, and mixins are good for layering providers. The harness uses classes where the dsh design is genuinely object-shaped; the kernel does not require them.
- Structs with `racket/generic`. This is the default for Service Definitions that have several providers (`gen:llm-adapter`, `gen:fs-provider`): the generic interface is the definition, a struct that implements it is a provider.
- Typed Racket for service types. Rejected for the kernel: services are provided and replaced at run time by code loaded at run time, and every typed boundary would become a contract anyway.

See [ADR 0005](../adr/0005-services-contracts-and-static-inject.md).

### 4.5 Events

**Chosen:** a listener table on the root from event name (a symbol such as `'tools/pre-execute`) to an immutable list of `hook` structs. Registration is an effect. The five dispatch functions reproduce section 3.6 exactly, including `prepend`, the `global` flag, the dispatch filter and the `next()`-called-twice error.

`waterfall` is ordinary continuation-passing: each listener receives a `next` procedure that runs the remainder of the chain. Nothing more exotic is needed, and the guide uses it to explain that "middleware" is the same idea as a continuation passed explicitly.

`parallel` runs each listener as a task and waits for all of them.

A macro, `define-event`, declares an event once in its Service Definition module: name, dispatch mode, parameter contracts and, for `waterfall`, the result contract. It generates a dispatcher and a registration form. Two classes of error disappear:

- A misspelled event name is an unbound identifier instead of a listener that is never called.
- An event can only be dispatched in its declared mode, because only that dispatcher exists. dsh enforces the same rule with an `@mode` documentation tag and a gate that compares declarations with dispatch sites.

The string-keyed functions remain, because configuration files, the plugin porter and dynamically written plugins need them.

### 4.6 Asynchrony, scheduling and the fiber state machine

This is the decision with the widest consequences. See [ADR 0002](../adr/0002-cooperative-tasks-on-threads.md).

Cordis runs on one JavaScript event loop. Code runs to completion between `await` points; transitions are promises; ordering is microtask order. Racket has preemptive green threads, first-class synchronizable events in the style of Concurrent ML, and first-class continuations. Three designs were considered.

1. **Preemptive threads with locks or actors.** Each fiber transition is a thread; shared structures are protected by locks or owned by manager threads. This is idiomatic for a server but it changes the semantics: two plugins loading at the same time register their listeners in a nondeterministic order, and listener order is observable in every `waterfall`. It also makes every piece of harness state a concurrency hazard, and it means a TypeScript handler body cannot be translated faithfully, because the original relied on not being interleaved.
2. **A reactor with continuation-based `await`.** One thread runs all harness code; `await` captures a delimited continuation and returns to the loop. This is JavaScript's model rebuilt from Racket's primitives. It is elegant, but a task is then not a thread, so it cannot be interrupted with a break, cannot be killed by a custodian while it loops, and blocking library calls stall everything.
3. **Cooperative tasks on threads.** A task is a Racket thread, but only the holder of a per-root *baton* runs harness code. `(await evt)` releases the baton, blocks on any Racket event, and takes the baton back in FIFO order before returning. Between two awaits a task cannot be interleaved with another task, which is the run-to-completion guarantee of JavaScript; and because a task is a real thread, breaks, custodians, parameterizations, exception handlers and `dynamic-wind` all behave normally.

**Chosen: design 3.** The baton is granted by a small manager thread that owns the queue and watches the holder with `thread-dead-evt`, so a task that is killed while holding the baton cannot deadlock the kernel. This is the kill-safe manager pattern from Flatt and Findler's work on kill-safe abstractions.

Consequences for the mapping:

- The paper's `create_task` (Algorithm 5, footnote 2) is `spawn-task`. `fiber.inertia` is the task of the transition in flight.
- A fiber is a synchronizable event (`prop:evt`) that becomes ready when no transition is in flight, so `await fiber` in TypeScript is `(await fiber)` here and `(sync fiber)` from outside the task world.
- Anything asynchronous in the kernel API is an *awaitable*: a task, a fiber, or any Racket `evt`. Timeouts and cancellation are `choice-evt` with an alarm or a cancellation event, not a separate mechanism.
- Blocking work that touches no harness state (HTTP reads, subprocess waits) runs through `(blocking thunk)`, which runs the thunk on a plain thread outside the baton and awaits it.
- Cancellation is a break delivered to the task's thread; `await` reacquires the baton before the break exception propagates, so cleanup code still runs under the baton.
- The scheduler is deterministic: with the same inputs, tasks run in the same order. Scripted end-to-end sessions can therefore be compared byte for byte.

Continuations are still used where they are the natural tool: generators for effect iterators, and escape continuations for early exit. They are not used to implement tasks.

The state machine itself is a direct transcription of Algorithm 5 into this model. The target is a list `(revision provider-uid ...)` or `#f`, compared with `equal?`.

### 4.7 Plugins as data

**Chosen:** a plugin is a struct `(plugin name inject config-schema provides apply meta)` with `prop:procedure`. `define-plugin` builds one. A plain procedure of two arguments is also accepted, as in Cordis, and so is a struct with an `apply` field made by the porter.

A module language, `#lang cordis/plugin`, lets a file *be* a plugin: its header keywords are the declaration and its body is the plugin body. The language generates a `plugin-info` submodule that holds the declaration (name, injections, config schema, provided services, declared tools and events) as plain data. The loader can read that submodule without instantiating the plugin. In Node the equivalent information is split between `package.json`, exported constants and whatever the module does when imported; here the declaration is data because the program is data. This is what makes it possible to check, before anything runs, that every plugin named in a profile exists, that its configuration validates, and what it asks for. The paper's section 6.3 observes that statically declared injections let an orchestrator review capabilities at load time; the submodule is that review surface.

### 4.8 Loading and unloading while the harness runs

**Chosen:**

- Plugin code is resolved from a name to a module path by a resolver table and loaded with `dynamic-require` inside the loader's namespace.
- Hot reload uses `racket/rerequire` to re-declare changed modules and their dependents, after which the loader updates the affected entries. An entry update disposes the old fiber and mounts the new plugin value; the kernel's own guarantees (inverses, then custodian) make the old instance disappear. File watching uses `filesystem-change-evt`, which the task model can await like any other event.
- Model-written and third-party plugins can be loaded in a `racket/sandbox` evaluator with limits on memory, time, file paths and network, and with the kernel module attached so that kernel structs are shared. Section 6.3 of the paper says sandboxing needs a boundary outside the language; Racket's sandbox and custodian limits provide a meaningful one inside the same process, with the usual caveat that it is not a security boundary against a determined attacker.

**Where this does not line up:** a Racket module instance cannot be removed from a namespace; re-declaration replaces the declaration, and old instances live as long as something references them. Node's module cache has the same property. The kernel's job is to make sure nothing references them: every registration made by the old instance is an effect and is reverted.

### 4.9 Configuration schemas

Schemastery is a combinator library whose values are both validators and descriptions. The Racket counterpart is a small schema DSL in `cordis-loader` whose combinators produce a struct carrying a validator, a default, documentation and a JSON rendering in Schemastery's serialisation, so that tools reading a dsh config catalog keep working. The combinators are ordinary functions; a `define-config` macro adds a struct-like accessor layer so that a misspelled config field in plugin code is a compile-time error.

## 5. Where Lisp and Scheme ideas line up with Cordis, and where they do not

**They line up:**

1. *Closures.* A revertible effect is a closure that captures the state it restores. The paper names closures as the first requirement of a host language.
2. *Lexical and dynamic scope.* Cordis needs both a definition site and a use site and builds them from proxies. Scheme has had names for both since `fluid-let`, and Racket's parameters are the principled form of the second.
3. *`dynamic-wind`.* It is the oldest statement in the Lisp family of "an action paired with its inverse, enforced by the runtime", and it handles re-entry, which is more than `try/finally`. Its limitation is its scope, which is the dynamic extent of a call.
4. *Custodians.* A hierarchy of resource owners, where shutting down a node reclaims everything beneath it, is the same tree as the fiber tree. Racket had this in 1999 for exactly the plugin-like case of running student programs inside DrRacket.
5. *Code as data.* A plugin's declaration can be read without running the plugin, and a configuration row and a plugin form are the same kind of value. The loader's "declarative component loader with configuration reconciliation" (paper section 5.2) is a program that manipulates descriptions of programs.
6. *Macros.* The paper says compile-time metaprogramming can replace an interception primitive and can check dependency declarations statically. `define-plugin`, `define-service` and `define-event` do both.
7. *First-class modules and namespaces.* Introducing and retracting code at run time is the paper's second temporal requirement. `dynamic-require`, `namespace-attach-module` and re-declaration provide it.
8. *Generators and continuations.* An effect iterator is a generator. The paper remarks that a language could compile effect iteration to a state machine; a generator is the library version of that.
9. *Synchronizable events.* "Wait for this fiber to settle, or for cancellation, or for a timeout, whichever comes first" is one `sync` over a `choice-evt`.
10. *Contracts.* Dependency typing with blame fits the provider and consumer roles.

**They do not line up:**

1. *Custodian shutdown is not an inverse.* It reclaims; it does not restore. It has no order, so the coeffect-ordering guarantee cannot be obtained from custodians alone. It also does not unwind killed threads.
2. *`dynamic-wind` and escape continuations assume one thread of control.* Cordis effects are installed in one activation and reverted in a later one by a different task.
3. *Parameters are not component-scoped.* A stored closure runs under its caller's parameterization. A design that relied only on `current-context` would attribute effects to the wrong fiber. The kernel therefore binds the context lexically in plugin bodies and re-establishes the parameter when it calls stored callbacks.
4. *Racket threads are preemptive.* The JavaScript kernel's correctness depends on run-to-completion. Racket code that mutates shared tables from two threads is wrong. The cooperative task layer restores the assumption; without it most of the kernel would need locks.
5. *Units are static.* They give the best static account of "what does this component need" in the Racket world, and they have no reactive part.
6. *No transparent interception.* Racket has chaperones and impersonators, which are how contracts are implemented and which could imitate the tracing proxies. Using them would hide which context an operation uses. The port prefers an explicit argument.
7. *Module instances cannot be unloaded individually.* Reload replaces declarations; old instances are collected only when unreferenced.
8. *Open-world static typing.* TypeScript's declaration merging lets any package extend the type of the context. Racket has no equivalent in the untyped language, and Typed Racket's types are closed at module boundaries. The port uses compile-time registries (macros that record declarations) and contracts instead.
9. *Reversibility of control.* Racket can re-enter a continuation, which invites the idea of "undoing" by jumping back. That restores control state, not the store, and has nothing to do with revertible effects. The analysis mentions it only to rule it out.

## 6. What the Racket kernel keeps, changes and adds

**Kept exactly:** the effect contract, LIFO disposal, nested effects, the service store with realms, strict and non-strict reads, the checked read and its error cases, in-place `set`, interception layering, the fiber states and the inertial state machine, target computation from provider identities, dependents-first unload ordering, failure recording and recovery through update, the five dispatch modes, `prepend`, `global`, dispatch filters, and the `internal/*` events.

**Changed, with the same observable behaviour for configuration and ported plugins:** property access becomes `ctx-ref` or lexical bindings; promises become awaitables; `this.ctx` rebinding becomes an explicit or parameter-supplied context; class-based `Service` becomes a plugin form that provides a value.

**Added (Racket extensions, each recorded in an ADR and none required by dsh configuration):** a custodian per fiber; static `inject` checking; `define-event` mode enforcement; the `plugin-info` submodule; sandboxed plugin loading with resource limits; break-based cancellation of tasks; deterministic scheduling.

## 7. Laws the kernel is tested against

These come from the paper's theorems and from the vendored specs. Each is a test or a property test in `racket/cordis/tests/`.

1. *Reversal.* For any sequence of effects installed by a fiber, disposing the fiber leaves the listener table, service store and property table equal to their state before the fiber was created.
2. *LIFO.* Inverses run in reverse order of installation; a nested effect's inverses run as part of its parent's inverse.
3. *Single shot.* A disposer runs its inverses at most once, and a second call returns the result of the first.
4. *Setup failure rolls back.* An effect whose thunk raises after yielding inverses runs those inverses and leaves nothing registered.
5. *No effect while unloading.* Creating an effect on a disposed or unloading fiber raises.
6. *Activation follows satisfaction.* A fiber is `ACTIVE` only if every injected name has an active provider in its realm, and becomes pending when one is withdrawn.
7. *Provider replacement reloads.* Replacing a provider with another, even one that provides an equal value, reloads dependents; replacing the value in place with `ctx-set!` does not.
8. *Coeffect ordering.* While a dependent's inverses run, `ctx-ref` of the dependency still returns the provider's value; the provider's inverses start only after all dependents have unloaded.
9. *Inertia.* A target change during a transition does not interrupt it; the fiber chains into the next transition when it completes.
10. *Cascade.* Disposing a fiber disposes its child fibers first.
11. *Isolation.* A service provided in one realm is invisible in another, and notifications do not cross realms.
12. *Dispatch modes.* Each mode's ordering, short-circuit and error behaviour as in section 3.6.
13. *Confluence for independent plugins.* Loading two plugins that do not depend on each other in either order yields the same store and the same listener set.
14. *Custodian backstop.* A thread, port or listener created by plugin code and never disposed is gone after the fiber unloads.
15. *Kill safety.* Killing a task at any point does not prevent other tasks from running.

## 8. Open questions

- How much of `ctx.accessor` and `ctx.mixin` the port needs beyond supporting translated plugins that write `ctx.<name>`.
- Whether effect iterators should be interruptible at every `yield` during reload, as in the paper, or only between top-level effects, as in the vendored source's synchronous iterator path.
- Whether sandboxed plugin namespaces should share the loader's module registry or attach only the kernel.
